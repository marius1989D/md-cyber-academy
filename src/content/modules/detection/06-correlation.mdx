Module 5 ended on a process tree, and that tree was legible because everything in it came from one log source on one host. Real intrusions are not so tidy. They start in a cloud identity, execute on an endpoint, and leave through a proxy — three products, three log formats, three separate low-severity alerts that individually justify nothing.

Correlation is the work of assembling those into one incident. It is also where a SOC's alert volume problem is genuinely solved rather than merely tuned, because fifty alerts about one intrusion becoming one incident about one intrusion is a fifty-fold reduction with no loss of detection.

## Three reasons to correlate

Worth separating, because they need different mechanisms:

- **Weak signals in combination.** A new sign-in country is weak; a large upload is weak; together with execution on the user's endpoint they describe an account takeover. This is the risk-based alerting case from Module 4.
- **Confidence from crossing tactics.** One alert in Execution is a maybe. An alert in Execution *plus* Credential Access *plus* Exfiltration on the same entity within an hour is qualitatively different — it is the shape of an intrusion rather than the shape of a false positive. Legitimate software rarely produces a full attack chain.
- **Volume reduction.** Grouping related alerts into one incident is a queue improvement that costs no coverage.

## The hard part: deciding what is the same thing

Here is the problem nobody warns you about. Correlation is trivial once you can join records; **the difficulty is entirely in the join.**

One human being appears in your telemetry as:

| Source | How they appear |
|---|---|
| Entra ID sign-in log | `j.hartley@corp.local` (UPN) |
| Windows Security log | `CORP\jhartley` (SAM account name) |
| Mail gateway | `james.hartley@corp.com` (external address) |
| Proxy log | `10.10.9.14` — an IP, with no user at all |
| EDR | a device GUID and a logged-on-user field |

None of those strings match each other. Correlating on "user" requires a resolution layer that knows they are one identity, and correlating that proxy record requires knowing which host held `10.10.9.14` **at 09:48 on that date** — which is a DHCP lease question, not a security question.

<Callout type="key">
This is the module's real lesson: **identity and asset resolution is correlation infrastructure, and it is usually the missing piece.** DHCP logs, an asset inventory, and a mapping between account naming conventions are not administrative paperwork — without them, cross-source correlation is guesswork.

It is also why Module 3's normalisation work pays off here rather than there. Schemas like ASIM and OCSF exist so that a source IP is the same field name everywhere; entity resolution is the next layer up, ensuring the *values* refer to the same real-world thing. Get one without the other and you can join fields that do not mean the same thing, which is worse than not joining at all because the result looks authoritative.
</Callout>

Microsoft Sentinel implements this as **entity mapping**: each analytics rule declares which fields represent which entities, using **identifiers** — attributes sufficient to identify the entity. Microsoft's guidance is that "using multiple strong identifiers will enable greater correlation between data sources", which is the whole principle in one sentence.

The limits are worth knowing because they bite quietly: up to **three identifiers** per entity, up to **ten entity mappings** per rule, and up to **500 entities per alert** divided equally across the mappings defined — so five mappings gives each one a 100-entity ceiling. There is also a hard **64 KB** size limit on the entities area of an alert, beyond which entities are simply **dropped**. An alert on a noisy behaviour can therefore silently lose the very entity you needed to correlate on.

## Sequence, count and order

Once you can join, you specify the pattern. Sigma's correlation types name the four shapes you will actually use:

- **`event_count`** — count events in a window. Brute force: 50 failures in five minutes.
- **`value_count`** — count *distinct* values of a field. Enumeration: one account requesting 40 distinct service names, which is exactly the Kerberoasting fan-out from the network course.
- **`temporal`** — several different event types within a window, in any order.
- **`temporal_ordered`** — the same, but the events must occur in the sequence given.

Each takes a **`group-by`** (the join key — the entity) and a **`timespan`**. That structure is worth internalising because it is platform-independent: every correlation engine is some version of *group by this entity, over this window, require this pattern*.

Choose `temporal_ordered` carefully. Order carries real information — credential theft *after* a suspicious sign-in tells a different story from the reverse — but it makes the rule dependent on timestamp accuracy across sources, and Module 3 already established that timestamps are the least trustworthy field you have. If your sources disagree by minutes, an ordered rule fails silently while the unordered version works.

## Declared rules correlate; undeclared rules do not

There is a consequence of all this that turns Module 1's documentation discipline into an operational requirement.

Sentinel's **Fusion** engine correlates signals across products into multistage-attack incidents, described by Microsoft as "low-volume, high-fidelity, and high-severity", comprising two or more alerts, and mapped to stages of the kill chain. It surfaces them as *incidents* in the `SecurityIncident` table rather than as alerts in `SecurityAlert`.

The requirement is the interesting part: analytics rules "must contain kill-chain (tactics) and entity mapping information in order to be used by Fusion".

Read that again in the context of Module 1's ADS framework. **Categorization** — declaring which ATT&CK tactic a rule addresses — looked like documentation hygiene. It is not. A rule that does not declare its tactic and does not map its entities is invisible to the correlation engine: it can fire, but it cannot contribute to an incident. Undocumented detections do not merely age badly; they are excluded from the mechanism that would have made them valuable.

## Assembling one incident

Rung 3. Three alerts, three products, over 34 minutes. Each was triaged separately and closed. Decide what was missed.

```text
09:14  Entra ID sign-in    Low       Sign-in from unfamiliar country
                                     user: j.hartley@corp.local
                                     result: success, MFA satisfied

09:31  Endpoint (Sysmon)   Medium    Office application spawned PowerShell
                                     host: WS-4471   user: CORP\jhartley

09:48  Proxy               Low       240 MB upload to file-sharing domain
                                     src: 10.10.9.14   user: (not logged)
```

Separately: a travelling user, a noisy macro rule, and someone using Dropbox. Together, across three ATT&CK tactics in 34 minutes on one identity: **T1078.004** valid cloud account, **T1204.002** user execution, **T1041** exfiltration. That is an intrusion, and it was in the queue the whole time as three closed tickets.

Now the honest part, because this is what the module is actually teaching. Joining alert one to alert two requires knowing `j.hartley@corp.local` and `CORP\jhartley` are one person — an identity mapping. Joining alert three requires knowing `WS-4471` held `10.10.9.14` at 09:48 — a DHCP lease lookup, since the proxy logged no user at all. **Neither join is a detection problem. Both are inventory problems.** A team with a resolved identity and asset layer raises one high-severity incident here; a team without it closes three tickets and finds out later.

<Callout type="warn">
Two failure modes in the other direction, because correlation can be overdone.

**Over-grouping.** Correlate too aggressively — a broad window, a weak join key like a shared NAT address or a service account used estate-wide — and unrelated activity merges into one enormous incident. Analysts then cannot tell which parts belong together, and genuine findings get buried inside a container that is technically one ticket. A NAT egress IP is a particularly bad join key: it groups the whole office.

**Windows that are too narrow.** Real intrusions dwell. Credential theft may follow initial access by days, not minutes. A 15-minute correlation window is cheap to run and will miss any adversary who is not in a hurry, which is most of the competent ones.

There is no correct universal window. What is correct is choosing it deliberately, per pattern, with a stated reason — and revisiting it when it produces either one giant incident or none at all.
</Callout>

<Lab title="Correlate three sources into one incident" host="Detection lab + your log platform (Sentinel free tier or Elastic)" minutes={70}>

You are going to build the identity resolution layer first, then a correlation rule that depends on it — in that order, because reversing it is the mistake this module exists to prevent.

1. **Inventory your identifiers.** For one test user in your lab, list exactly how they appear in every log source you collect: UPN, SAM account, email address, host name, device ID, current IP. Write the actual strings side by side.
2. **Build the resolution map.** Produce a small lookup — a watchlist, index, or CSV — that maps those representations to one canonical identity. Do the same for host-to-IP, using your DHCP or lease data.
3. **Generate a chain.** Across at least two sources, produce a benign version of the worked example: a sign-in from an unusual source, then a distinctive process execution on that user's host, then an outbound transfer. Note the wall-clock time of each.
4. **Try to correlate naively.** Write a rule that joins the sources on the user field as it appears natively, with no resolution layer. Confirm it does not match, and record why.
5. **Correlate properly.** Rewrite it using your resolution map as the join key. Confirm it now assembles the chain into one result.
6. **Test the window.** Run your rule with a 5-minute, 1-hour and 24-hour window. Record which windows catch your chain and which miss it, then state the window you would deploy and justify it against realistic adversary dwell time.
7. **Break it deliberately.** Change your rule to `temporal_ordered` and then shift one source's clock by ten minutes (or simply correlate on ingestion time instead of event time). Confirm the ordered rule stops matching while the unordered one still works.
8. **Check the join key quality.** Identify one weak join key in your environment — a NAT address, a shared service account, a generic host name — and state what would happen if you correlated on it.

**Evidence of completion:** a journal entry with (a) your side-by-side identifier table for one user across all sources, (b) the resolution map you built, (c) the naive rule failing and the resolved rule succeeding, with both queries, (d) your window comparison across three durations and the justified choice, and (e) the result of the clock-skew test showing ordered correlation failing. Item (a) is the deliverable most worth keeping: being able to say out loud how one identity appears in five products, and what maps them together, is the difference between describing correlation and having done it.

</Lab>
