Module 1 left a rule on the table with 90% recall and 0.9% precision — one real alert in every 112. Tuning is the work that turns that into something a human can act on. It is the least glamorous part of detection engineering and the part that decides whether a SOC functions, so it is worth defining precisely rather than treating as "making the noise stop".

**Tuning is raising precision while protecting recall.** Both halves matter. Anyone can silence a rule; the skill is silencing the noise without silencing the detection.

## Two ways to fail, one of them invisible

An under-tuned rule produces alert fatigue. The queue fills, analysts triage by pattern-matching rather than investigating, and eventually the rule gets acknowledged-and-closed on sight. Note what has happened: the rule still fires, dashboards still show it working, and it has stopped detecting anything. **An ignored alert is functionally a false negative** — the attack passes through a control everyone believes is operating.

An over-tuned rule is worse because it is quieter. Exclusions accumulate, each individually justified, until the rule covers a fraction of the behaviour it names. Nobody notices, because — Module 1 again — silence looks like safety.

Both failures end in a missed attack. Only the first one is visible before it happens, which is why over-tuning is the more dangerous habit and the one that needs deliberate discipline.

## The tuning ladder, best to worst

Not all tuning is equal. Work down this ladder and only move to the next rung when the one above genuinely cannot solve it:

1. **Sharpen the hypothesis.** Often the rule is detecting a category when the malicious version has a distinguishing property. Not "process accessed LSASS" but "process accessed LSASS with a handle requesting memory read, from an image outside the expected set". This raises precision and costs no recall, because you are describing the attack more accurately rather than looking away from part of it.
2. **Add context.** Enrich with asset criticality, user role, whether the source is signed, whether the destination is rare in the estate. Context turns one undifferentiated stream into a stream you can rank.
3. **Threshold and aggregate.** One failed logon is nothing; eighty in a minute is something. Aggregation also collapses fifty alerts about one incident into one alert about one incident, which is a queue improvement with no detection loss.
4. **Scope.** Run the noisy rule only where it is meaningful — domain controllers, servers holding regulated data — and accept reduced coverage elsewhere *as a recorded decision*.
5. **Exclude.** Last resort. You are explicitly telling the system not to look somewhere.

Most teams start at rung 5 because it is the fastest. That is precisely why their detections decay.

## Exception hygiene, and the logic error that costs you

If you must exclude, the shape of the exclusion decides how much you gave away. Here is the distinction that matters most, and it is genuinely easy to get wrong.

Suppose a backup agent legitimately triggers your LSASS rule. You know three things about it: its full path, that it is signed by a known vendor, and which servers it runs on. Compare two ways of writing the exception:

```text
BROAD -- each condition excluded independently
  where SourceImage       != "acmebkp.exe"
  where SignatureStatus   != "Valid"

  Drops any event matching EITHER condition.
  You have just excluded every signed process in the estate.

NARROW -- exclude only when the conditions co-occur
  where not( SourceImage     == "C:\\Program Files\\AcmeBackup\\acmebkp.exe"
         and SignatureStatus == "Valid"
         and Signer          == "Acme Corp Ltd" )

  Drops only the specific combination you actually investigated.
```

Chained exclusion clauses are ANDed together by the query engine, so each one removes events on its own — the union of everything you listed. To exclude a *combination*, the negation has to wrap the whole conjunction. Get this backwards and a single exception can blow a hole through the entire rule while looking, in review, like three careful conditions.

<Callout type="warn">
This is worth checking rather than trusting, including in vendor documentation — published examples of "fine-grained" exclusions sometimes chain the conditions in a way that is logically identical to the broad form they are contrasting themselves with. If you cannot state in one sentence which events an exclusion removes, do not deploy it.

Test it the direct way: run the rule's query with the exclusion applied *as a select rather than a filter* — show me the events this exception will hide — and read them. If that set contains anything you would want to know about, the exception is wrong.
</Callout>

## Make exceptions expire

The most under-used control in tuning is time. An exception written during a migration, a pen test, or a noisy software rollout is correct for that week and wrong for the next year — but nobody revisits it, because there is no prompt to.

Microsoft Sentinel's automation-rule exceptions default to expiring after 24 hours, and Microsoft's stated reason is exactly this: a time limit "reduces the chance of false negative errors". Adopt the principle whatever platform you use. **Every exception should carry an owner and an expiry date**, and a permanent exception should be a deliberate decision someone signed, not the default outcome of nobody looking.

There is also a division of labour worth knowing, because it comes up in interviews. Sentinel offers two routes: **automation rules**, which create exceptions without touching the analytics rule, apply across several rules, keep an audit trail of the closure reason, and are typically created by analysts; and **analytics rule modifications**, which support boolean and subnet logic and centralised exception lists via watchlists, are more flexible and complete, and are typically implemented by SOC engineers. The general lesson: analysts should be able to suppress noise safely and reversibly without editing detection logic.

<Callout type="key">
**Every exclusion is a blind spot you now own.** That is not a reason to avoid them — it is a reason to record them where they will be read. Each one belongs in the ADS **Blind Spots and Assumptions** section from Module 1, with the reason, the owner and the expiry.

Do that consistently and your exception list becomes the honest answer to "what would this rule miss?", which is the question an interviewer asks and the question an incident asks. Skip it and you have a rule whose real coverage lives only in the query, where nobody reads it.
</Callout>

## When individually weak signals are all you have

Some behaviours are never conclusive alone. A user logging in from a new country is weak. A large download is weak. An MFA method being registered is weak. Alert on each and you drown; ignore each and you miss the account takeover they collectively describe.

**Risk-based alerting** inverts the model: instead of each rule raising an alert, each contributing observation adds a risk score to an entity — a user, a host — and an alert is raised only when accumulated risk crosses a threshold within a window. Detections that could never justify an alert individually become useful contributors, and the alert that eventually fires arrives with its supporting evidence already assembled.

The trade-off is honest: you have added a scoring model that itself needs tuning, and a poorly-weighted one produces confident nonsense. But for the large class of signals that are suspicious only in combination, it is the difference between having a detection and not.

## Judging a tuning request

Rung 3. This lands in your queue. Decide before reading on.

```text
FALSE POSITIVE REPORT
  Rule:       Suspicious process access to LSASS  (T1003.001)
  Volume:     412 alerts / 24h, all triaged as benign
  Cause:      Backup agent acmebkp.exe reading LSASS during nightly job
  Affects:    340 file servers
  Requested:  exclude where SourceImage contains "acmebkp.exe"
```

The request is understandable and the exclusion is dangerous. `contains "acmebkp.exe"` matches the filename **anywhere in any path**, so an attacker who drops a binary of that name in `%TEMP%`, or names their tool `evil-acmebkp.exe`, is now invisible to your best credential-theft detection. You have handed the adversary a documented allowlist entry, and filename-based exclusions are exactly what an operator looks for.

Work the ladder instead. **Sharpen** first: does the backup agent request a different `GrantedAccess` mask than a credential dumper? If so, the malicious case can be described more precisely and the false positives vanish with no exclusion at all. If not, **add context**: exclude on the full path *and* a valid signature *and* the expected signer, combined so all must hold. Then **scope** it to the 340 servers where the backup agent actually runs, so a workstation triggering it still alerts. Record the residual blind spot: an attacker who compromises the backup vendor's signing key, or who abuses the legitimate agent on those specific servers, is not covered.

That is four minutes of extra thought and the difference between a tuned rule and a deleted one.

<Lab title="Tune your Module 1 rule and prove you did not break it" host="Detection lab VM + your log platform" minutes={60}>

You are taking the validated detection you built in Module 1 and putting it through a real tuning cycle, with measurements either side so the improvement is demonstrated rather than asserted.

1. **Baseline.** Run your rule over at least 24 hours of lab activity. Record total alerts, and triage every one as true or false positive. Calculate the observed precision. This is your before figure.
2. **Categorise the noise.** Group the false positives by root cause rather than listing them. Most rules have two or three causes producing most of the volume.
3. **Sharpen first.** For the largest cause, find a property that distinguishes the malicious case — an access mask, a parent process, a path, a signature status. Rewrite the rule logic to use it. Do not write any exclusion yet.
4. **Re-measure.** Run the sharpened rule over the same 24-hour window. Record the new precision and, critically, **re-run your Atomic Red Team test** to confirm the rule still fires on the real behaviour. A precision improvement that breaks detection is not an improvement.
5. **Now exclude, carefully.** For any remaining cause you cannot sharpen away, write a combined exception where all conditions must co-occur. Before deploying it, run the exception as a *select* — list the events it will hide — and read them.
6. **Add expiry and ownership.** Give each exception an owner and a review date, recorded wherever your team would actually find it.
7. **Document the blind spots.** Update the ADS Blind Spots and Assumptions section with every exclusion, in the form: what is hidden, why, who owns it, when it expires, and how an attacker could deliberately land inside it.
8. **Deliberately over-tune, then undo it.** Add the broad version of one exclusion (a substring match on a filename). Re-run your atomic test and confirm the rule now misses the real attack. Record that result, then revert.

**Evidence of completion:** a journal entry with (a) before and after precision figures over the same window, (b) proof the sharpened rule still fires on the atomic test, (c) the list of events each exception hides, produced before deployment, (d) your updated Blind Spots section with owners and expiry dates, and (e) the result of step 8 showing the over-tuned rule failing its own validation test. Item (e) is the one to keep: being able to demonstrate that you tested whether your tuning broke the detection is the difference between claiming to tune carefully and having evidence of it.

</Lab>
