Every module so far has assumed a human reads the alert. That assumption is what made Module 1's arithmetic survivable: a rule at 0.9% precision wastes analyst time, which is bad but recoverable. This module removes the human from the loop, and the moment you do that, **the cost of a false positive changes from wasted time to disabled accounts and isolated machines.**

Extended detection and response is the product category that does this. Understanding where it genuinely helps — and where the marketing outruns the engineering — is the point here.

## XDR next to SIEM, honestly

Both correlate. The difference is what they own.

| | SIEM (Sentinel) | XDR (Defender) |
|---|---|---|
| **Data** | Anything you can ship it | Deep telemetry from that vendor's own products |
| **Correlation** | Rules and models you configure over normalised data | Native, because it owns the entity graph across its workloads |
| **Custom logic** | Unlimited | Constrained to its schema and query surface |
| **Response** | Via playbooks you build | Built in, and able to act on its own estate directly |
| **Blind spot** | Whatever you did not onboard | Anything outside the vendor's ecosystem |

The honest summary: **XDR buys depth and native action inside one ecosystem; SIEM buys breadth and arbitrary logic across everything else.** Most real SOCs run both, which is why Microsoft is consolidating Sentinel into the Defender portal (Module 7's 2027 date). Treat "XDR replaces SIEM" as a sales position rather than an architecture.

What XDR genuinely does better is Module 6's hard problem. Entity resolution across endpoint, identity, email and cloud app is difficult for you and trivial for the vendor, because it already knows that this device, this mailbox and this Entra account belong to one person. You are not doing clever correlation there — you are inheriting a join key you would otherwise have to build.

## Custom detections: your rules, their response

Defender's **custom detections** are the bridge between everything you have learned and the platform's response capability. You write an advanced hunting KQL query — Module 7's skill, unchanged — set it to run at intervals, and it generates alerts *and takes automatic response actions* on matches.

Two details worth carrying:

- You can create one directly from the advanced hunting query editor, which makes Module 8's HMM4 loop — hunt, then operationalise — a two-click transition rather than a project.
- Custom detections can be **managed as code** in GitHub or Azure DevOps (currently preview, via the Microsoft Security BICEP extension). That is Module 11's subject arriving early, and it is the difference between rules that are reviewable and rules that live in a portal nobody audits.

## The precision bar for automated action

Here is the number that should anchor your thinking. For automatic containment actions, Microsoft states it maintains a **confidence level of 99% or higher**, based on real production data, where confidence means detector precision measured as signal-to-noise ratio.

Put that next to Module 1. A rule at 90% recall and 0.9% precision was a reasonable *alerting* candidate after tuning. It would be catastrophic as an *action* trigger: 1,000 false positives a day, each one now disabling an account or isolating a laptop. The service desk would be overwhelmed by lunchtime and the capability would be switched off by Friday — permanently, because trust does not come back.

<Callout type="key">
**The precision required to alert and the precision required to act are different by orders of magnitude, and this is the judgement the role actually tests.**

A useful way to hold it: alerting spends *analyst time*, and you can afford to be wrong often because the cost of each error is minutes. Acting spends *business availability*, and the cost of each error is somebody unable to work, or a domain admin locked out mid-incident. So the question for any rule is not "is this good enough to fire" but "is this good enough that I would let it act unsupervised at 3am on a Sunday with nobody watching".

For almost everything you write, the answer is no — and that is the correct answer, not a failure. Automated response belongs on the small set of detections where the behaviour is unambiguous and the containment is cheap to undo.
</Callout>

## What automatic disruption actually does

Microsoft's **automatic attack disruption** is worth knowing concretely, because it is the reference implementation of this idea. It operates at the **incident** level rather than on a single indicator — a distinction the documentation draws explicitly against blocking based on one IOC — and its available actions include:

- **Contain device** and **isolate device** — policy applied across onboarded endpoints so they refuse communication with the compromised machine.
- **Contain IP** — the same, for a device that is not onboarded and therefore cannot be isolated directly.
- **Disable user** in Active Directory or Entra ID, **suspend user**, and **revoke user session** to cut active tokens — note that last one, which is the direct answer to Module 3's stolen-refresh-token problem.
- **Contain user** — blocking that identity's communication at the endpoint layer across all onboarded devices.

Three design properties matter more than the action list, and they are what make automation defensible:

1. **Every automatic action can be undone** by the security team.
2. **Exclusions** can be configured for critical users, devices and IP addresses that must never be contained automatically.
3. **Detectors are validated in audit mode** before broad release, and deployed gradually.

Those three are the template for any automation you build yourself. If your own automated response is not reversible, not excludable, and not run in audit mode first, you have built something more dangerous than the threat.

## Deciding what may act

Rung 3. Three rules are proposed for automatic response. Decide each before reading on.

```text
RULE A  Known ransomware file-encryption behaviour on an endpoint
        Precision (measured, 90d):  99.4%
        Proposed action:            isolate device
        Reversible:                 yes, from the portal

RULE B  Impossible travel sign-in
        Precision (measured, 90d):  31%
        Proposed action:            disable user account
        Reversible:                 yes

RULE C  LSASS memory access from an unsigned binary
        Precision (measured, 90d):  88%
        Proposed action:            isolate device
        Reversible:                 yes
```

**Rule A: yes.** Precision is at the bar, the behaviour is unambiguous, and the counterfactual is decisive — the cost of *not* isolating during live encryption dwarfs the cost of wrongly isolating one machine. This is exactly the case automation exists for.

**Rule B: no, and it is the trap.** 31% precision means two of every three actions disable an innocent user, and impossible travel is notoriously noisy — VPNs, mobile roaming, and a phone syncing mail through a different egress all produce it. Worse, the *blast radius is misjudged*: disabling an account can lock someone out of everything mid-shift, and if it fires on a domain admin during an incident you have removed your own responder. Alert on it; do not act on it.

**Rule C: not yet, and the reason is the useful one.** 88% is good — this is a strong rule — but roughly one in eight isolations would be wrong, which is a helpdesk ticket and a lost afternoon each time. The right move is not to discard it but to **raise its precision first**, using Module 4's ladder: sharpen the hypothesis, add signature and path context, scope to server groups. Then re-measure. Automation is the reward for a detection that has earned it, not a substitute for tuning one.

Note what all three judgements had in common: **a measured precision figure over a real window.** Without that number the conversation is opinion, and no responsible person will let your rule touch production.

<Callout type="warn">
Two failures specific to this territory.

**Automation as a tuning substitute.** A noisy rule does not become acceptable because the response is automatic; it becomes more expensive. If you find yourself hoping automation will make an alert-fatigue problem go away, you have the causality backwards.

**Losing the analyst's judgement.** When containment happens before anyone looks, the investigation still has to happen — and now it starts from a changed environment, with the adversary aware they have been detected. Automatic disruption buys time; it does not close the incident. Someone still has to determine scope, and the disruption tagging on the incident is the starting point for that work, not the end of it.
</Callout>

<Lab title="Measure precision, then decide what may act" host="Defender XDR trial or Microsoft 365 Developer tenant" minutes={60}>

You are going to build a custom detection from a hunting query, measure its precision honestly, and produce a written decision about whether it may take automatic action. The decision document is the deliverable — it is exactly the artifact a senior engineer would ask you for.

1. **Set up.** Use a Defender XDR trial or Developer tenant with at least one onboarded test device. Never a production tenant.
2. **Start from a hunt.** Take a query from Module 8's hunt, or write one in advanced hunting against `DeviceProcessEvents`. Confirm it returns results on behaviour you can generate.
3. **Create a custom detection** from the advanced hunting editor. Set the frequency, map entities, and set the alert title and severity. Do **not** attach a response action yet.
4. **Measure precision properly.** Run it for as long as you practically can — at minimum several days of lab activity, ideally with the test device used normally. Triage every alert as true or false positive and calculate precision. Record the observation window and total alert count alongside the figure; a percentage without a denominator is not a measurement.
5. **Write the automation decision.** For your rule, document: measured precision with window and sample size, the proposed action, the blast radius if wrong (who is affected and for how long), whether the action is reversible and how, what exclusions you would configure, and your verdict — automate, alert only, or tune first.
6. **If your verdict is "tune first", do it.** Apply one improvement from Module 4's ladder, re-measure, and record whether precision moved.
7. **Test a response action safely.** On a device you own, attach a low-impact response action (or manually perform the isolate action and then undo it) and record how long isolation took to apply, how the device behaved, and exactly how you reversed it. Knowing the undo path *before* you need it is the point.
8. **Write the exclusion list.** Name the assets and accounts in your environment that must never be automatically contained, and justify each in one line.

**Evidence of completion:** a journal entry with (a) the custom detection query and configuration, (b) your measured precision with the observation window and total alert count, (c) the one-page automation decision covering blast radius, reversibility, exclusions and verdict, (d) evidence of the response action being applied and successfully reversed with timings, and (e) your exclusion list with justifications. Item (c) is the portfolio artifact: being able to argue in writing why a rule may or may not act unsupervised is a more senior skill than writing the rule was.

</Lab>
