Most people in security can talk about prompt injection. Very few can talk credibly about the AI supply chain, which is exactly why it is worth owning. It is where traditional software supply chain security meets a category of risk that has no equivalent outside ML: **a model file that executes code the moment you load it.** If you understand nothing else from this module, understand that — it is the single fact that reframes a downloaded model from "data" to "untrusted executable."

## What a model file actually is

A trained model is weights plus the code needed to reconstruct the object that holds them. How those two are packaged determines whether loading the file is safe. The dominant historical format in the Python ecosystem is **pickle**, and pickle is not a data format — it is a serialised *program*.

Python's `pickle` module serialises objects by recording instructions for rebuilding them. Among those instructions is `__reduce__`, which can specify an arbitrary callable to invoke during unpickling. That means a pickle file can carry a payload that runs when the file is deserialised — before you have done anything with the "model" at all.

```python
# The entire vulnerability, in miniature.
import pickle, os

class Payload:
    def __reduce__(self):
        # Whatever this returns is CALLED at unpickle time.
        return (os.system, ("id > /tmp/pwned",))

# An attacker ships this as "model.pkl". You load it:
# pickle.load(open("model.pkl","rb"))  ← command runs here, no model needed
```

<Callout type="warn">
`torch.save()` and `torch.load()` use Python's pickle by default, so a `.pt`, `.pth` or `.bin` "PyTorch model" from a random repo is a pickle. **The default hardened in PyTorch 2.6: `torch.load` now passes `weights_only=True` unless you supply your own `pickle_module`.** That restricts the unpickler to tensors and a few primitive types and forbids dynamic imports during load — PyTorch's own wording is that it "narrows the surface of remote code execution attacks", not that it closes it, and it explicitly does not defend against denial of service.

Know exactly where the hole still is, because this is what separates a current answer from a two-year-old one:

- **`weights_only=False`.** PyTorch's own error text says re-running with it "can result in arbitrary code execution". Plenty of code and plenty of tutorials still set it, because it is the fastest way to make a load error go away.
- **Anything not PyTorch.** `joblib.load` and most scikit-learn `.pkl` artifacts are plain, unrestricted pickle. No `weights_only` exists to save you.
- **Old runtimes.** Pre-2.6 PyTorch defaults to the unrestricted unpickler.

The load-time execution itself is **AML.T0018.002 Embed Malware**; the victim opening the artifact is **AML.T0011.000 Unsafe AI Artifacts**. Publishing the poisoned model to a hub in the first place is **AML.T0058**. Name the right one — an interviewer who knows ATLAS will notice.
</Callout>

## The attack surface, laid out

The AI pipeline has more untrusted-input points than a traditional software build, because it pulls artifacts and data from many places:

- **The model hub.** A public hub is an app store with far weaker gatekeeping. Typosquatted repos, a legitimate account compromised, or a popular model reuploaded with a poisoned pickle — all observed in the wild.
- **The dataset.** Training and fine-tuning data pulled from public sources is a poisoning vector (Module 3) and a licence/PII liability.
- **The dependencies.** The ML stack is a deep tree — `transformers`, `torch`, CUDA libraries, hundreds of transitive packages. Ordinary software supply chain risk, at ML scale.
- **The pre-trained base.** Backdoors survive fine-tuning, so an inherited base model is inherited risk (Module 3's warning).

## The format shift that fixes the worst of it

The ecosystem's answer to the pickle problem is **safetensors** — a format that stores *only* tensors and metadata, with no mechanism to execute code on load. It is the reason "just use safetensors" has become standard advice.

| | pickle (`.pkl`, `.pt`, `.bin`) | safetensors (`.safetensors`) |
|---|---|---|
| Can execute code on load | **Yes** | No |
| Stores arbitrary Python objects | Yes | Tensors + metadata only |
| Safe from untrusted sources | No | Yes (by design) |
| Load speed | Slower | Faster (zero-copy, mmap) |

Preferring safetensors removes the *arbitrary-code-execution* risk. It does **not** remove poisoning or backdoor risk — the weights themselves can still be malicious. Safetensors makes loading safe; it does not make the model trustworthy. Those are two different problems and conflating them is a common mistake.

## Defending the pipeline

Treat this as software supply chain security with ML-specific additions:

- **Provenance.** Pull models and datasets only from sources you can attribute, prefer signed artifacts, and pin versions/hashes rather than floating tags. Verify the hash you got matches the hash you expected.
- **Prefer safetensors**, and when you must handle a pickle from outside, scan it (tools like `picklescan` / `fickling` inspect for dangerous opcodes) and deserialise it in a sandbox with no network and no credentials — never on your workstation or a build agent with secrets.
- **An ML-BOM.** Extend the SBOM idea to models and datasets: record every model, base, and dataset with its source and hash, so when a hub repo is found poisoned you can answer "did we ever pull that?" in seconds.
- **Least privilege at load.** The process that loads a model should hold nothing worth stealing — no cloud keys, no write access beyond its scratch space.

<Callout type="detect">
The load step is your detection chokepoint. Loading a model should not spawn a shell, open a socket, or touch the filesystem outside its working directory. In a hardened pipeline, run model loads under a syscall monitor (even a simple `strace`/eBPF rule) and alert on `execve`, outbound connections, or writes outside scratch during deserialisation. A model that phones home while loading has already told you everything you need to know.
</Callout>

<Lab title="Weaponise and then defang a pickle" host="2018 MBP attack box — isolated VM, no network" minutes={55}>

Do this in a throwaway VM with networking off. You are proving the mechanism to yourself; treat the payload as live.

1. Write a class whose `__reduce__` returns a harmless-but-visible action — `(os.system, ("touch /tmp/PWNED",))`. Pickle an instance to `model.pkl`.
2. In a fresh Python process, `pickle.load` it. Confirm `/tmp/PWNED` appears — code ran with no model involved.
3. Install `picklescan` and run it against your file. Confirm it flags the dangerous opcode *without* executing it.
4. Re-save a genuine small model (train a trivial sklearn classifier) as **safetensors** (or `skops`), and confirm loading it performs no such action.
5. Bonus: run the malicious load under `strace -f -e trace=execve,network` and capture the `execve` line — the detection signal from the callout.

**Evidence of completion:** a journal entry with (a) the proof that `pickle.load` executed your payload, (b) picklescan's flagged output, and (c) the `strace` line showing the `execve` at load time. You now have a demonstrable, defensible account of the single most differentiating risk in AI security — worth its own slide in any interview.

</Lab>
