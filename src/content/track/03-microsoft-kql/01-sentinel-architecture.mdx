<Why asked="How does Microsoft Sentinel relate to Log Analytics, and how does an alert become an incident?">
You already know what a SIEM does in the abstract from Phase 2. This step makes it
concrete in the platform that dominates UK job specs. Learning the architecture
before the query syntax matters because almost every KQL problem a beginner hits
is actually an architecture problem - querying a table that was never connected,
searching a retention tier that no longer holds the data, or wondering why forty
alerts did not group into one incident. Understanding the plumbing prevents you
blaming the language.
</Why>

## Sentinel sits on Log Analytics

This is the first thing to get straight, and it is a common interview opener.

**Log Analytics** is the underlying data platform: a workspace that ingests,
stores and queries log data with KQL. It is not security-specific - it serves
Azure Monitor and application telemetry too.

**Microsoft Sentinel** is the SIEM and SOAR layer enabled *on top of* a Log
Analytics workspace. It adds data connectors, analytics rules, incidents, entity
behaviour, threat intelligence, workbooks and automation.

<Callout type="key">
The one-line version: *"Log Analytics is the data platform and query engine.
Sentinel is the security layer enabled on a workspace - it adds detection,
incident management, threat intel and automation. The KQL is the same either way,
which is why KQL skills transfer straight into Azure Monitor and Defender."*
</Callout>

## Workspace design

One workspace or many is a real architectural decision:

- **Single workspace** - simplest, cheapest, queries span everything with no
  cross-workspace syntax. Default choice.
- **Multiple workspaces** - needed for data residency (UK data must stay in UK
  South), tenant separation in an MSSP, or hard RBAC boundaries between business
  units.

Cross-workspace queries are possible with `workspace("name").TableName`, but they
add complexity and can add cost. For an MSSP, Sentinel supports **Azure Lighthouse**
delegated access so analysts work across many customer tenants from one place -
worth naming, because it is exactly how the MSSPs you are targeting operate.

## Getting data in

**Data connectors** are the packaged integrations - Entra ID, Defender XDR, Office
365, AWS, firewalls, syslog. Many are one-click; others need an agent or a
collector.

**Data Collection Rules (DCRs)** define *what* the Azure Monitor Agent collects
and where it goes. This is where selectivity happens, and it is the lever for
both signal quality and cost. You built one in the Phase 5 lab step.

**Table plans** are the cost control most people never learn, and they map neatly
onto the retention tiering from Phase 2:

| Plan | Query capability | Typical use |
|---|---|---|
| **Analytics** | Full KQL, powers analytics rules | Security-critical tables you detect on |
| **Basic / Auxiliary** | Limited operators, cheaper ingest, no analytics rules | High-volume, low-detection-value logs kept for investigation |
| **Archive** | Requires a search job or restore | Long-tail retention for compliance and retrospective hunting |

<Callout type="warn">
A table on a Basic or Auxiliary plan **cannot back a scheduled analytics rule**.
Putting a noisy but occasionally-valuable firewall table on Basic to save money
silently removes your ability to detect on it. That trade-off is a genuine
architectural decision and a good thing to raise unprompted - it shows you think
about cost and detection together rather than treating them as separate problems.
</Callout>

## Analytics rules

Five types, and knowing which is which is exam and interview material:

- **Scheduled** - your own KQL, running on a defined cadence over a lookback
  window. The workhorse; this is what you will write.
- **Near-real-time (NRT)** - runs approximately every minute against incoming data.
  Limited in what it can express, but low latency for high-severity cases.
- **Microsoft Security** - creates Sentinel incidents from alerts raised by
  Microsoft products such as Defender. Pass-through rather than detection.
- **Fusion** - Microsoft's multi-stage attack correlation, combining low-fidelity
  signals across sources into a high-fidelity incident.
- **Anomaly** - built-in behavioural models you enable and tune with thresholds.

A scheduled rule carries: the query, the schedule and lookback, an alert
threshold, **entity mapping**, **event grouping**, **incident grouping**, and
optional automation.

## Alerts, entities and incidents

This is the part that generates the most confusion, so be precise:

```text
  Query matches  →  ALERT  →  grouped by rules  →  INCIDENT  →  investigation
                      |                                |
                 entity mapping                   automation rules
                 (account, host, IP,               (assign, tag, run
                  file, URL, mailbox)               playbook, close)
```

**Entity mapping** tells Sentinel which columns in your query results represent
real-world objects - an account, a host, an IP, a file hash, a URL. Without it:

- The investigation graph is empty, so you cannot pivot visually
- UEBA cannot attribute behaviour to an identity
- **Incident grouping by entity does not work**, so related alerts stay separate

**Event grouping** controls whether one rule run produces a single alert for all
matched rows, or one alert per row. **Incident grouping** controls whether alerts
from the same rule combine into one incident, and over what time window.

## Automation

**Automation rules** are the lightweight layer: on incident creation, assign an
owner, add a tag, change severity, or close automatically. Simple conditional
logic, no code.

**Playbooks** are Azure Logic Apps triggered by an incident or alert. They can
enrich (look up threat intel, query an asset database), notify (Teams, email), or
act (disable an account, isolate a device). Enrichment playbooks are the high-value
starting point, and they connect directly to the SOAR module in your Detection
Engineering course.

## The rest, briefly

- **Watchlists** - reference tables you join against: VIP users, approved admin
  hosts, asset criticality. Excellent for enrichment and exclusions.
- **Workbooks** - dashboards built on KQL.
- **UEBA** - behavioural baselining per entity, surfaced as anomaly scores.
- **Threat intelligence** - indicator feeds via TAXII or the upload API, matched
  against your data.
- **RBAC** - Sentinel Reader, Responder and Contributor roles, layered over Azure
  resource permissions.

<Scenario
  step="track/03-microsoft-kql/01-sentinel-architecture"
  id="incident-grouping"
  title="Forty alerts that should have been one incident"
  minutes={9}
>
<div slot="brief">

A customer complains that a single attack generated 40 separate incidents,
swamping their queue overnight. You are asked to work out why.

```text
RULE: "Suspicious sign-in from anonymising infrastructure"
Type: Scheduled · runs every 5 min · lookback 5 min

QUERY (abridged)
  SigninLogs
  | where TimeGenerated > ago(5m)
  | where ResultType == 0
  | where RiskLevelDuringSignIn == "high"
  | project TimeGenerated, UserPrincipalName, IPAddress,
            AppDisplayName, DeviceDetail

CONFIGURATION
  Entity mapping:      (none configured)
  Event grouping:      "Trigger an alert for each event"
  Incident grouping:   "Group alerts into a single incident if all
                        entities match"  ·  window 5 hours
  Alert threshold:     greater than 0

WHAT HAPPENED
  02:10 - 04:55  One attacker IP, one compromised account,
                 40 successful high-risk sign-ins to various
                 apps as they enumerated the tenant.
  Result: 40 alerts -> 40 incidents.
```

Explain why, and specify exactly what you would change.

</div>
<div slot="model">

**Root cause: incident grouping is set to group by matching entities, but no
entity mapping is configured. With no entities to match on, no two alerts can
ever be considered related, so every alert becomes its own incident.**

This is the single most common Sentinel misconfiguration, and it is invisible
until an incident actually occurs - the rule looks correct, fires correctly, and
produces unusable output.

**The two settings interacting:**

1. **Event grouping is "trigger an alert for each event."** Forty matching rows
   produced forty alerts. That is not wrong in itself - per-event alerts preserve
   detail and are often what you want - but it means the grouping configuration is
   now doing all the work.
2. **Incident grouping is "if all entities match", and there are no entities.**
   The grouping logic has nothing to compare, so the comparison never succeeds.
   Forty alerts, forty incidents.

**What I would change, in order:**

**a. Configure entity mapping.** This is the actual fix and it is mandatory
regardless of anything else:

```text
Account   →  UserPrincipalName
IP        →  IPAddress
```

Grouping now has something to match on, so the forty alerts from one account and
one IP collapse into one incident. This also restores the investigation graph and
lets UEBA attribute the behaviour - both of which are currently broken and nobody
had noticed.

**b. Reconsider the grouping strategy.** "All entities match" is strict: if the
attacker rotated IPs mid-session, the account would match but the IP would not,
and you would split into multiple incidents again. I would set grouping to match
on **the Account entity only**, with the IP retained as a mapped entity for
investigation. An incident is best organised around *who was affected*, and one
compromised identity should be one incident even if the attacker moved between
addresses.

**c. Keep the 5-hour grouping window**, or extend it. Five hours comfortably
covered this 02:10-04:55 activity. If anything I would raise it toward the length
of a shift so that continuing activity attaches to the open incident rather than
opening a fresh one after the window lapses.

**d. Consider whether per-event alerting is right here.** Grouped alerting - one
alert summarising all matched events per run - would reduce the volume further.
The trade-off is that grouped alerts carry less per-event detail in the alert
itself, though the underlying events remain queryable. For a high-severity
identity rule I would keep per-event and rely on correct grouping, because the
detail matters during investigation.

**What I would not do:** raise the alert threshold or lengthen the schedule to
suppress volume. The rule detected a genuine attack correctly and promptly - the
detection is working. The failure is entirely in how its output was assembled, and
tuning the detection to fix a presentation problem would reduce real coverage.

**The general lesson:** entity mapping is not an optional nicety. It underpins
incident grouping, the investigation graph, UEBA attribution and most automation
conditions. A rule without entity mapping is a rule whose output cannot be
correlated with anything, and reviewing existing rules for missing entity mapping
is a genuinely valuable thing to volunteer doing in a new job.

</div>
</Scenario>
