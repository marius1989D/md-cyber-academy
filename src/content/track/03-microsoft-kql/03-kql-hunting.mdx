<Why asked="What's the difference between threat hunting and detection?">
Detection answers questions you already knew to ask. Hunting asks the questions
nobody wrote a rule for - and every rule that exists started life as a hunt. For a
Tier 1 candidate, being able to hunt is the single clearest signal that you will
not stay Tier 1 for long, and quiet hours on a night shift are exactly when it
happens. The queries below are the shapes that find things: first-seen,
statistical outlier, and cross-source correlation.
</Why>

## Hunting versus detection

| | Detection | Hunting |
|---|---|---|
| Trigger | Automated, continuous | Human, hypothesis-driven |
| Input | A known bad pattern | A theory about attacker behaviour |
| Output | An alert | A finding, or a new detection rule |
| Assumes | We know what to look for | Something is here that we missed |
| Success | The rule fired | Either a finding, or confidence in its absence |

<Callout type="key">
A hunt that finds nothing is not a failed hunt. "We hypothesised X, searched for
it thoroughly, and found no evidence" is a genuine result that increases
confidence and often exposes a telemetry gap along the way. Saying this in an
interview separates you from candidates who think hunting means finding something
every time.
</Callout>

**Structure a hunt in four steps:** form a hypothesis specific enough to be wrong
("an attacker is using WMI for lateral movement"), identify the data that would
show it, query and analyse, then act - escalate a finding, or convert the query
into a scheduled rule so the hunt never has to be repeated manually.

## The operators that make hunting possible

Beyond the fundamentals, five carry most of the weight:

- **`make-series`** - build an evenly-spaced time series with gaps filled, which
  is a precondition for the anomaly functions.
- **`series_decompose_anomalies`** - decomposes a series into seasonal, trend and
  residual components and flags points that deviate. Handles daily and weekly
  rhythms automatically, which naive thresholds cannot.
- **`arg_max` / `arg_min`** - return the whole row where a column hits its
  extreme. `arg_max(TimeGenerated, *)` gives the latest full record per group.
- **`materialize()`** - cache a subquery used more than once so it is computed
  once. On a hunt over 30 days this is the difference between seconds and a timeout.
- **`join kind=leftanti`** - what is in A but not in B. The first-seen workhorse.

Also worth knowing: **`externaldata`** pulls a CSV or JSON from a URL into a
query, which lets you join against an IOC list without ingesting it, and
**`row_window_session`** groups events into sessions separated by idle gaps.

## The three hunt shapes

Almost every useful hunt is a variation on one of these:

1. **First-seen** - this host pair, this parent-child process, this user-agent, has
   never been observed before. Cheap, high-yield, hard for an attacker to avoid.
2. **Statistical outlier** - this volume, timing or ratio deviates from the
   established baseline for this entity.
3. **Cross-source correlation** - this identity event and this device event, close
   in time, are individually unremarkable but jointly suspicious.

## Challenge 1 - first-seen parent-child

<QueryChallenge
  step="track/03-microsoft-kql/03-kql-hunting"
  id="first-seen-parentchild"
  title="Never-before-seen process lineage"
  lang="kql"
  tables={["DeviceProcessEvents", "DeviceName", "FileName", "InitiatingProcessFileName", "ProcessCommandLine", "Timestamp"]}
>
<div slot="brief">

Hunt for parent-child process relationships seen in the **last 24 hours** that
have **never** occurred in the preceding **30 days**, anywhere in the estate.

Return the pair, how many devices it appeared on, and a sample command line.
Order so the rarest appear first.

</div>
<div slot="solution">

```kql
let baseline = materialize(
    DeviceProcessEvents
    | where Timestamp between (ago(31d) .. ago(1d))
    | distinct InitiatingProcessFileName, FileName
);
DeviceProcessEvents
| where Timestamp > ago(1d)
| join kind=leftanti baseline
    on InitiatingProcessFileName, FileName
| summarize
    Devices     = dcount(DeviceName),
    Executions  = count(),
    FirstSeen   = min(Timestamp),
    SampleCmd   = any(ProcessCommandLine),
    DeviceList  = make_set(DeviceName, 20)
    by InitiatingProcessFileName, FileName
| sort by Devices asc, Executions asc
```

**Why the shape is what it is:**

- **`materialize()`** on the baseline matters here. Without it the 30-day
  `distinct` may be recomputed, and on a real estate that is the difference
  between a query that returns and one that times out.
- **`between (ago(31d) .. ago(1d))`** excludes the last 24 hours from the
  baseline. If today were included, today's activity would match itself and the
  query would silently return nothing - the same off-by-one from the fundamentals
  step, and it fails without error, which is worse.
- **Sorting ascending on device count** is deliberate. A new lineage on one device
  is far more interesting than one that appeared on 400 devices this morning, which
  is almost certainly a software deployment.

**Common wrong shapes:** including `DeviceName` in the baseline `distinct`, which
turns an estate-wide hunt into a per-device one and floods you with results;
sorting descending, which buries the interesting findings; and omitting
`materialize`, which works fine in a lab and fails in production.

**Tuning note:** the first run will return a large amount of legitimate novelty -
new software, updates, patched binaries. That is expected. The value comes from
running it regularly so the baseline matures and the daily new-lineage count drops
to something reviewable.

</div>
</QueryChallenge>

## Challenge 2 - statistical anomaly with seasonality

<QueryChallenge
  step="track/03-microsoft-kql/03-kql-hunting"
  id="series-anomaly"
  title="Anomalous authentication volume per account"
  lang="kql"
  tables={["SigninLogs", "UserPrincipalName", "TimeGenerated", "ResultType"]}
>
<div slot="brief">

Corporate sign-in volume has a strong daily and weekly rhythm - quiet at night,
quiet at weekends. A fixed threshold either alerts every Monday morning or misses
a real spike on a Tuesday.

Over **21 days**, build an hourly series of successful sign-ins **per account** and
flag statistically anomalous points, accounting for that seasonality.

</div>
<div slot="solution">

```kql
let start = ago(21d);
let stop  = now();
let step  = 1h;
SigninLogs
| where TimeGenerated between (start .. stop)
| where ResultType == 0
| make-series Signins = count()
    on TimeGenerated
    from start to stop step step
    by UserPrincipalName
| extend (anomalies, score, baseline) =
    series_decompose_anomalies(Signins, 2.5, -1, 'linefit')
| mv-expand
    TimeGenerated to typeof(datetime),
    Signins       to typeof(long),
    anomalies     to typeof(int),
    score         to typeof(double),
    baseline      to typeof(long)
| where anomalies == 1 and Signins > baseline
| where TimeGenerated > ago(2d)
| project TimeGenerated, UserPrincipalName, Signins, baseline, score
| sort by score desc
```

**How it works:**

- **`make-series`** produces an evenly spaced series with empty buckets filled -
  a hard requirement for the anomaly functions, which cannot handle irregular
  gaps. `summarize by bin()` will not do here.
- **`series_decompose_anomalies`** splits the series into seasonal, trend and
  residual parts and scores each point against the residual. **This is what
  handles the daily and weekly rhythm automatically** - the reason a fixed
  threshold fails.
- **The `2.5` threshold** is sensitivity in standard deviations. Lower catches
  more and alerts more; 2.5 to 3 is a reasonable starting range.
- **`-1`** lets the function infer seasonality rather than being told the period.
- **`anomalies == 1`** keeps positive deviations only. Value `-1` marks dips,
  which matter for a different hunt - an account that suddenly *stops*
  authenticating, or a log source that goes quiet, which is the pipeline failure
  from Phase 2.
- **`Signins > baseline`** is belt and braces alongside the `== 1` filter.
- **Filtering to the last 2 days at the end**, after the full series is built,
  keeps 21 days of context for the model while returning only recent findings.

**Common wrong shapes:** using `summarize count() by bin(TimeGenerated, 1h)`
instead of `make-series`, which produces gaps the decomposition cannot handle;
forgetting `mv-expand`, which leaves you with arrays rather than rows; and
filtering to recent time *before* building the series, which destroys the baseline
the model needs.

</div>
</QueryChallenge>

## Challenge 3 - cross-source correlation

<QueryChallenge
  step="track/03-microsoft-kql/03-kql-hunting"
  id="cross-source"
  title="Sign-in followed by suspicious device activity"
  lang="kql"
  tables={["SigninLogs", "DeviceProcessEvents", "DeviceLogonEvents", "AccountName", "UserPrincipalName"]}
>
<div slot="brief">

Individually unremarkable, jointly suspicious: a sign-in from an unfamiliar
location, followed within **30 minutes** by process execution on a device under
the same account that has a suspicious parent.

Correlate identity and endpoint telemetry over the last 7 days.

</div>
<div slot="solution">

```kql
let window = 30m;
let risky_signins = materialize(
    SigninLogs
    | where TimeGenerated > ago(7d)
    | where ResultType == 0
    | where RiskLevelDuringSignIn in ("high", "medium")
        or DeviceDetail.isCompliant == false
    | extend Account = tolower(tostring(split(UserPrincipalName, "@")[0]))
    | project SigninTime = TimeGenerated, Account, UserPrincipalName,
              IPAddress, Location = tostring(LocationDetails.countryOrRegion)
);
let suspicious_exec = DeviceProcessEvents
    | where Timestamp > ago(7d)
    | where InitiatingProcessFileName in~
        ("winword.exe","excel.exe","outlook.exe","powerpnt.exe","mshta.exe")
    | extend Account = tolower(AccountName)
    | project ExecTime = Timestamp, Account, DeviceName,
              FileName, ProcessCommandLine, InitiatingProcessFileName;
risky_signins
| join kind=inner suspicious_exec on Account
| where ExecTime between (SigninTime .. SigninTime + window)
| project SigninTime, ExecTime,
          MinutesAfter = datetime_diff('minute', ExecTime, SigninTime),
          UserPrincipalName, IPAddress, Location,
          DeviceName, InitiatingProcessFileName, FileName, ProcessCommandLine
| sort by SigninTime desc
```

**The technique to take away:**

- **Normalising the join key is the whole problem.** `SigninLogs` carries a UPN
  (`p.osei@corp.com`); `DeviceProcessEvents` carries a bare account name
  (`p.osei`). Both go through `tolower()` and the UPN is split at the `@`. Joins
  across Microsoft tables fail far more often on key format than on logic, and
  this is the fix.
- **`materialize` on the first subquery** because it feeds the join.
- **The time-window filter comes after the join**, since you need both timestamps
  in scope to compare them.
- **`in~`** is the case-insensitive membership operator - process names vary in
  casing across sources and a case-sensitive `in` will quietly miss rows.

**Common wrong shapes:** joining on the raw `UserPrincipalName` against
`AccountName` and getting zero rows with no error; applying the window filter
inside a subquery where only one timestamp exists; and using `join kind=leftouter`
here, which returns every risky sign-in whether or not anything followed.

**Extending it:** this shape generalises. Swap the endpoint side for
`DeviceNetworkEvents` to find sign-ins followed by unusual outbound connections,
or for `DeviceLogonEvents` to find sign-ins followed by lateral movement. The
pattern - risky identity event, then device event, within a window - is one of the
most productive hunts available in a Microsoft estate.

</div>
</QueryChallenge>
