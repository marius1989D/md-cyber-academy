## The shape of the language

KQL reads left to right, piping a table through operators. Once that clicks, the
whole language is small:

```kql
SecurityEvent                       // start with a table
| where TimeGenerated > ago(1h)     // filter early — always
| where EventID == 4625             // filter more
| summarize Attempts = count()      // aggregate
    by Account, IpAddress
| where Attempts > 10               // filter the aggregate
| sort by Attempts desc             // order
| take 20                           // limit
```

<Callout type="key">
**Filter early and filter on time first.** `where TimeGenerated > ago(1h)` as the
first line is not stylistic — it lets the engine skip most of the data before
doing anything else. On a real workspace the same query with time filtering last
can be a hundred times slower. Interviewers notice.
</Callout>

## The operators worth knowing cold

| Operator | Does | Note |
|---|---|---|
| `where` | Filter rows | Chain several; the engine optimises |
| `project` | Choose columns | `project-away` drops, `project-rename` renames |
| `extend` | Add a computed column | Where you do string parsing and maths |
| `summarize` | Aggregate | `count()`, `dcount()`, `min()`, `max()`, `make_set()`, `arg_max()` |
| `by` | Group | Follows `summarize` |
| `join` | Combine tables | `kind=inner`, `leftouter`, `leftanti` — `leftanti` is the one people forget |
| `union` | Stack tables | Useful across `DeviceEvents` and `SecurityEvent` |
| `bin()` | Bucket a value | `bin(TimeGenerated, 1h)` for time series |
| `ago()` / `now()` | Relative time | `ago(7d)`, `ago(90m)` |
| `has` / `contains` | String match | `has` is token-based and much faster — prefer it |
| `let` | Declare a variable | Use for thresholds and reusable sub-queries |

<Callout type="warn">
`contains` does a substring scan; `has` matches whole tokens and uses the index.
On a large table the difference is enormous. Reaching for `contains` by habit is
the most common performance mistake beginners make, and the easiest to fix.
</Callout>

## Challenge 1 — find the spray

<QueryChallenge
  step="track/03-microsoft-kql/02-kql-fundamentals"
  id="spray"
  title="Password spray detection"
  lang="kql"
  tables={["SecurityEvent", "EventID", "Account", "IpAddress", "TimeGenerated", "LogonType"]}
>
<div slot="brief">

Write a query that surfaces likely password spraying in the last 24 hours: a
single source IP producing failed logons (event 4625) against **more than ten
distinct accounts**, where each account has only a small number of attempts.

Return the source IP, the count of distinct accounts, the total attempts, and
the list of accounts targeted.

</div>
<div slot="solution">

```kql
SecurityEvent
| where TimeGenerated > ago(24h)
| where EventID == 4625
| summarize
    DistinctAccounts = dcount(Account),
    TotalAttempts    = count(),
    Accounts         = make_set(Account, 100),
    FirstSeen        = min(TimeGenerated),
    LastSeen         = max(TimeGenerated)
    by IpAddress
| where DistinctAccounts > 10
| extend AttemptsPerAccount = round(TotalAttempts * 1.0 / DistinctAccounts, 2)
| where AttemptsPerAccount < 5
| sort by DistinctAccounts desc
```

**Why the shape is what it is:**

- `dcount(Account)` is the spray signature — breadth, not depth.
- `AttemptsPerAccount` is what separates spraying from brute force. Without it,
  one account hammered 500 times would also match `DistinctAccounts > 10` if the
  attacker mixed both.
- `make_set(Account, 100)` caps the list so a huge campaign doesn't blow up the row.
- `FirstSeen`/`LastSeen` give you the window immediately, which is the first
  thing you need when you start triaging.

**Common wrong shapes:** filtering time last instead of first; using
`count()` alone without `dcount()`, which finds brute force rather than spraying;
forgetting that a NAT gateway or VPN concentrator will legitimately produce many
accounts from one IP, so this needs an exclusion list before it becomes a rule.

</div>
</QueryChallenge>

## Challenge 2 — the joins people get wrong

`leftanti` answers "what's in A that isn't in B", which is how you find things
that *should* have happened and didn't — the most under-used detection shape
there is.

<QueryChallenge
  step="track/03-microsoft-kql/02-kql-fundamentals"
  id="leftanti"
  title="First-time RDP between host pairs"
  lang="kql"
  tables={["SecurityEvent", "Computer", "IpAddress", "LogonType", "Account"]}
>
<div slot="brief">

Find RDP logons (logon type 10) in the **last 24 hours** where that specific
source-IP-to-destination-computer pair has **never** been seen in the preceding
**30 days**. This is one of the highest-value, lowest-cost lateral movement
detections you can build.

</div>
<div slot="solution">

```kql
let lookback = SecurityEvent
    | where TimeGenerated between (ago(31d) .. ago(1d))
    | where EventID == 4624 and LogonType == 10
    | distinct IpAddress, Computer;
SecurityEvent
| where TimeGenerated > ago(1d)
| where EventID == 4624 and LogonType == 10
| join kind=leftanti lookback on IpAddress, Computer
| project TimeGenerated, Account, IpAddress, Computer
| sort by TimeGenerated desc
```

**Why this works:** `leftanti` keeps only the rows on the left with no match on
the right — so what survives is a host pair that has never spoken RDP before.
The `let` block builds the baseline as a `distinct` pair list, which stays small
and fast even over 30 days.

**Note the `between (ago(31d) .. ago(1d))`.** If the baseline included the last
24 hours, today's activity would match itself and the query would return nothing.
That off-by-one is the single most common mistake in first-time-seen detections,
and it fails silently — which is worse than failing loudly.

**In production you'd add:** an exclusion for jump boxes and admin subnets,
otherwise the IT team's normal work floods it.

</div>
</QueryChallenge>

## Challenge 3 — time series and beaconing

<QueryChallenge
  step="track/03-microsoft-kql/02-kql-fundamentals"
  id="beacon"
  title="Regular-interval outbound connections"
  lang="kql"
  tables={["DeviceNetworkEvents", "DeviceName", "RemoteIP", "RemoteUrl", "InitiatingProcessFileName", "Timestamp"]}
>
<div slot="brief">

C2 beacons phone home on a regular interval. Write a query over the last 7 days
that finds device-to-remote-IP pairs with a **high number of connections** and a
**low variance in the gap between them** — the statistical fingerprint of
automated beaconing rather than human browsing.

</div>
<div slot="solution">

```kql
DeviceNetworkEvents
| where Timestamp > ago(7d)
| where ActionType == "ConnectionSuccess"
| where not(ipv4_is_private(RemoteIP))
| sort by DeviceName, RemoteIP, Timestamp asc
| extend PrevTime = prev(Timestamp)
| extend PrevKey  = strcat(prev(DeviceName), prev(RemoteIP))
| where PrevKey == strcat(DeviceName, RemoteIP)
| extend GapSeconds = datetime_diff('second', Timestamp, PrevTime)
| summarize
    Connections = count(),
    MeanGap     = avg(GapSeconds),
    StdDevGap   = stdev(GapSeconds),
    Process     = make_set(InitiatingProcessFileName, 5)
    by DeviceName, RemoteIP
| where Connections > 50
| extend Jitter = round(StdDevGap / MeanGap, 3)
| where Jitter < 0.15 and MeanGap > 30
| sort by Jitter asc
```

**The idea:** `Jitter` is the coefficient of variation — standard deviation over
mean. Human traffic is bursty and irregular, so jitter is high. A beacon sleeping
60 seconds ± 3 has jitter near zero. Modern C2 frameworks deliberately add jitter
to defeat exactly this, so a real rule sets the threshold higher and accepts more
false positives.

**`prev()` needs the sort.** Window functions in KQL operate on row order, so the
`sort by DeviceName, RemoteIP, Timestamp asc` is load-bearing, and the `PrevKey`
check stops you computing a gap across a boundary between two different pairs.

**Reality check:** this will also find software update checks, telemetry and
monitoring agents, which are the most regular traffic on any network. That's not
a flaw in the query — tuning it is the actual job, and Phase 5 step 3 is where
you learn to do it.

</div>
</QueryChallenge>
