This is the most-asked technical interview question in the industry, and it is
asked *because* it is unbounded — the interviewer watches how deep you can go
and stops you when you run out. It is also the substrate for everything else:

You need to actually have it.
</Why>

## The model that matters

Forget memorising seven OSI layers as a list. Learn the four that generate
telemetry you will look at, and what each one can tell you:

| Layer | You see | It answers |
|---|---|---|
| Link (Ethernet/ARP) | MAC addresses, ARP tables | Which physical device, and is someone poisoning ARP |
| Network (IP) | Source and destination IPs, TTL | Who talked to whom, roughly where they are |
| Transport (TCP/UDP) | Ports, flags, sequence numbers | What service, and whether the conversation completed |
| Application (HTTP/DNS/TLS/SMB) | Hostnames, URIs, certificates, SNI | What was actually being done |

The analyst's habit is to ask, at every layer, *what would this look like if
someone were lying to me?* A TTL that doesn't match the claimed OS. An SNI that
doesn't match the certificate. A DNS response with a suspiciously long subdomain.

## The handshake, and why it earns its own section

```
Client ──── SYN (seq=x) ─────────────▶ Server
Client ◀─── SYN-ACK (seq=y, ack=x+1) ─ Server
Client ──── ACK (ack=y+1) ───────────▶ Server
```

Three packets. Nearly every network detection concept hangs off understanding
them:

- **Closed port** replies `RST`, not `SYN-ACK`. That's how a port scan
  distinguishes open from closed, and why a burst of RSTs from one host to many
  ports is scanning (T1046).
- **SYN scan** sends SYN, gets SYN-ACK, sends RST instead of completing. Fast
  and historically quieter, because no session is established to log.
- **SYN flood** sends SYN and never completes, exhausting the server's
  half-open connection table.
- **Teardown** is `FIN`/`FIN-ACK` for a graceful close, `RST` for an abrupt one.
  Repeated RSTs mid-session are worth a look.

<Callout type="key">
Interview-grade phrasing: *"SYN, SYN-ACK, ACK establishes state on both ends.
A closed port answers with RST, which is the whole basis of port scanning, and a
half-open scan deliberately never sends the final ACK so the connection is never
fully established and historically wasn't logged by the application."*
</Callout>

## Ports you must know without thinking

Not a list to memorise for its own sake — these are the ones that appear in
alerts, and the ones an interviewer will fire at you rapidly.

**Everyday:** 20/21 FTP · 22 SSH · 23 Telnet · 25 SMTP · 53 DNS · 67/68 DHCP ·
80 HTTP · 110 POP3 · 143 IMAP · 389 LDAP · 443 HTTPS · 445 SMB · 3389 RDP

**Windows and AD:** 88 Kerberos · 135 RPC endpoint mapper · 137–139 NetBIOS ·
636 LDAPS · 3268 Global Catalog · 5985/5986 WinRM

**Suspicious by convention:** 4444 (Metasploit default) · 1080 (SOCKS proxy) ·
8080/8888 (proxies and dev servers in odd places) · 6667 (IRC, old-school C2)

The judgement to develop is not "port 4444 is bad" — it's *unusual for this
host*. A build server talking on 8080 is normal; an accountant's laptop doing it
at 3am is not.

## DNS, which is where the interesting things happen

DNS is the most abused protocol in enterprise networks, because it is almost
never blocked. Three patterns to recognise:

**Tunnelling (T1071.004).** Data encoded into subdomain labels:
`aGVsbG8gd29ybGQ.attacker.com`. Signals: abnormally long or high-entropy
subdomains, high query volume to one domain, TXT record queries from hosts that
have no business making them.

**Domain generation algorithms.** Malware generating hundreds of pseudo-random
domains to find its C2. Signals: a burst of NXDOMAIN responses from one host.

**Fast flux.** One domain resolving to many IPs with a very short TTL, to keep
takedowns hard.

<Lab title="Read your own traffic" host="M5 MacBook Pro" minutes={90}>

You have Wireshark-capable hardware and a Pi router already sitting between you
and the internet. Use it.

1. Install Wireshark. Capture on your active interface for sixty seconds while
   you load a single website.
2. Find the DNS query and response for that site. Note the query type, the
   response, and the TTL.
3. Find the TCP handshake to the resulting IP. Confirm SYN, SYN-ACK, ACK in
   order. Use `tcp.flags.syn == 1 && tcp.flags.ack == 0` to isolate connection
   starts.
4. Find the TLS Client Hello. Read the SNI field — this is the hostname in
   cleartext even on an HTTPS connection, and it is why SNI is a genuinely
   useful detection surface.
5. Now `nmap -sS` your own Pi router from the Mac while capturing. Watch the
   RSTs come back from closed ports. **This is what a port scan looks like in
   telemetry**, and you will be asked to describe it.

**Evidence to capture:** a screenshot of the handshake filtered, and a
screenshot of the scan's RST pattern. Log both in your evidence log.

</Lab>
