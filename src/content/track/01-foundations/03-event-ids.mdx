<Why asked="What's the difference between 4624 and 4625, and what do the logon types tell you?">
Windows event IDs are the vocabulary of a Microsoft-stack SOC, which in the UK
means almost every SOC. An interviewer uses them as a fast, unfakeable
competence check: you either know that 4688 carries process creation and that
command line auditing has to be switched on separately, or you don't. There is
no way to reason your way there in the moment. This is pure, high-yield memory
work, and two weeks of it changes how you interview.
</Why>

## The security log core

| ID | Event | What it proves | What it does *not* prove |
|---|---|---|---|
| 4624 | Successful logon | Someone authenticated, with a logon type | That it was the legitimate user |
| 4625 | Failed logon | An attempt failed, with a status code | That it was an attack |
| 4634 / 4647 | Logoff / user-initiated logoff | Session ended | Much on its own — useful for session duration |
| 4648 | Logon with explicit credentials | `runas`, or a process supplying creds | The creds were stolen |
| 4672 | Special privileges assigned | The session holds admin-equivalent rights | Anything malicious by itself |
| 4688 | Process creation | A process started, with parent | The command line, **unless** you enable it |
| 4697 / 7045 | Service installed | A new service was registered | Whether it is legitimate |
| 4720 | User account created | Account creation | Who authorised it |
| 4728 / 4732 / 4756 | Member added to a security group | Group membership change | Intent |
| 4768 / 4769 / 4771 | Kerberos TGT / TGS / pre-auth failed | Kerberos activity, with encryption type | — |
| 5140 / 5145 | Network share accessed / checked | Share access, with the share name | What was taken |
| 1102 | Audit log cleared | Someone cleared the security log | Always investigate. Always. |

### Logon types — the part people fluff

The type field on 4624 is where most of the meaning lives:

- **2 — Interactive.** At the console, physically or via a KVM.
- **3 — Network.** Something reached this host over the network: SMB share, remote
  WMI, most lateral movement. The single most common type you'll triage.
- **4 — Batch.** Scheduled task.
- **5 — Service.** A service starting under an account.
- **7 — Unlock.** Workstation unlocked.
- **8 — NetworkCleartext.** Credentials sent in cleartext — usually IIS basic auth. Worth flagging.
- **9 — NewCredentials.** `runas /netonly`. Frequently seen in pass-the-hash tooling.
- **10 — RemoteInteractive.** RDP.
- **11 — CachedInteractive.** Logged on with cached domain credentials, no DC reachable.

<Callout type="key">
Type 3 and type 10 are the two you'll live with. Type 3 is lateral movement's
natural habitat; type 10 is RDP, and an RDP logon to a server from a workstation
that has never done it before is one of the highest-value simple detections
there is.
</Callout>

### Failure codes on 4625

The status and sub-status fields tell you *why* it failed, and they distinguish
a fat-fingered password from an attack:

- `0xC000006A` — wrong password against a valid account. Volume here means brute force.
- `0xC0000064` — user does not exist. Volume here means **user enumeration or password spray**.
- `0xC0000234` — account locked out.
- `0xC0000072` — account disabled.
- `0xC000006F` / `0xC0000070` — outside permitted hours / from an unauthorised workstation.

The distinction between `6A` and `64` is a favourite interview question, because
it separates a candidate who has looked at real logs from one who has read a list.

## Sysmon — the telemetry Windows should have had

Sysmon is free, from Microsoft, and transforms endpoint visibility. The events
that earn their storage:

- **1 — Process creation.** Richer than 4688: hashes, parent, full command line, and the
  process GUID that lets you build a real process tree.
- **3 — Network connection.** Which process opened which connection. This is the
  event that ties a network alert to a binary.
- **7 — Image loaded.** DLL loads. Noisy, but it's how you catch DLL side-loading.
- **8 — CreateRemoteThread.** Classic process injection.
- **10 — ProcessAccess.** Something opened a handle to another process — the
  detection surface for LSASS credential dumping.
- **11 — File created.**
- **12/13/14 — Registry.** Run keys, service creation, persistence.
- **22 — DNS query.** Which process resolved which name. Extremely high value.

<Callout type="warn">
Do not deploy Sysmon with the default config — it will drown you. Use a curated
configuration (SwiftOnSecurity's is the standard starting point, Olaf Hartong's
modular one is the step up). Being able to say *"I deployed Sysmon with a tuned
config because the default generates unusable volume"* is a small sentence that
signals real experience.
</Callout>

## Triage it yourself

<Scenario
  step="track/01-foundations/03-event-ids"
  id="spray-or-noise"
  title="03:14 — a burst of failed logons"
  minutes={8}
>
<div slot="brief">

You pick up an alert titled *Multiple failed authentications — DC01*. The
underlying events, summarised:

```text
Time window: 03:11:40 – 03:13:02 (82 seconds)
Source host: 10.20.4.51 (WKSTN-0442)
Event ID:    4625  ×  63
Status:      0xC000006A  (58 events)
             0xC0000064  (5 events)
Accounts:    58 distinct accounts, 1 attempt each
             5 accounts appearing once, no other activity
Logon type:  3
Also in window:
  4624 × 1  — account svc_backup, logon type 3, from 10.20.4.51, 03:13:04
  4672 × 1  — same session, special privileges assigned
```

Write your triage. What is this, what do you check next, in what order, and what
is your escalation decision?

</div>
<div slot="model">

**What this is:** a password spray that succeeded, followed immediately by a
privileged logon. This is not a brute force — the give-away is *one attempt
against each of 58 accounts* rather than many attempts against one. Spraying
tries a single common password broadly to stay under lockout thresholds.

**The status code split matters.** `0xC000006A` means the account exists and the
password was wrong; `0xC0000064` means the account doesn't exist. Five
non-existent accounts alongside 58 valid ones tells you the attacker is working
from a list that is mostly, but not entirely, accurate — probably harvested
rather than enumerated live.

**The critical detail is the timeline.** The successful 4624 for `svc_backup`
lands two seconds after the failures stop, from the same source, same logon
type. That sequencing is the whole finding. Followed by 4672 — the account holds
privileges.

**What you check, in order:**

1. Is `svc_backup` supposed to authenticate from a workstation at all? Service
   accounts logging on from user endpoints is almost always wrong.
2. What did that session do next? Pull 4688/Sysmon 1 on both hosts, 5140/5145 for
   share access, and any 4648 or subsequent 4624s using those credentials.
3. Is WKSTN-0442 compromised, or is it the attacker's foothold? Check what was
   running on it before 03:11 — a spray originating from an internal workstation
   means that workstation is very likely already owned.
4. Scope: did the same source, or the same credential, touch anything else?

**Escalation decision: escalate now, don't finish investigating first.** You have
a successful privileged authentication immediately following a spray from an
internal host at 3am. That is a live incident. Escalate with what you have,
keep working while Tier 2 picks it up, and flag containment — isolating
WKSTN-0442 and disabling `svc_backup` — as a recommendation rather than an
action, because that call sits above Tier 1.

**What would change the conclusion:** if `svc_backup` normally authenticates from
that host at exactly 03:13 every night as part of a backup job, and the 58
failures resolve to a misconfigured script iterating an old account list, this
is a change-management problem rather than an intrusion. Check the pattern
against the previous seven nights before you commit — but check it *after* you've
escalated, not before.

</div>
</Scenario>
