<Why asked="A user's account shows a successful sign-in from an unusual country. Walk me through your triage.">
The perimeter moved. For most modern organisations the real front door is Entra
ID, and a huge share of actual incidents now begin with an identity — a phished
token, an MFA-fatigued user, a malicious OAuth consent — and never drop a single
file on an endpoint. A SOC that only watches endpoints misses these entirely.
This is the newest material in Phase 1, the part CEH doesn't touch at all, and
increasingly the first question in a modern SOC interview.
</Why>

## The model: identity as the control plane

In a cloud-first environment, **identity is the perimeter**. Entra ID (formerly
Azure AD) is Microsoft's identity provider, and the objects you'll triage against
are:

- **Users** and **groups** — as in on-prem AD, often synced from it.
- **Service principals** and **app registrations** — non-human identities for
  applications. Frequently over-permissioned and under-watched, which makes them
  a rising attack surface.
- **Managed identities** — Azure-assigned identities for resources, so code
  authenticates without stored secrets.
- **Conditional Access policies** — the rules engine: *if* this user, from this
  location, on this device, *then* require MFA / block / grant. This is where much
  of the actual security lives, and gaps in it are what attackers hunt for.

<Callout type="key">
The mental shift from the AD step: on-prem you think in tickets and hashes; in
the cloud you think in **tokens and consent**. An access token or refresh token
is the cloud equivalent of a Kerberos ticket — steal it and you're authenticated
without a password *and without triggering MFA*, because MFA already happened
when the token was issued.
</Callout>

## The log that matters: Entra sign-in logs

The sign-in logs are your 4624 for the cloud. The high-value fields:

- **Result** — success or failure, plus a failure reason code.
- **IP address and location** — geo-derived, the basis of impossible-travel.
- **Application** — what was being signed into.
- **Conditional Access** — which policies applied and what they did.
- **Authentication requirement** — single-factor or multi-factor, and *how* MFA
  was satisfied.
- **Device** — managed/compliant or unknown.

Two failure reason codes worth recognising, because they distinguish attack
shapes:

- **50126** — invalid username or password. Volume across many accounts is cloud
  password spraying (T1110.003).
- **50053** — account locked, or *smart lockout* triggered. A cluster suggests an
  active spray being throttled.
- **50074 / 500121** — MFA challenge not satisfied / failed. A run of these against
  one user, followed by a success, is the MFA-fatigue signature.

The other essential log is the **audit log** — directory changes: consent grants,
role assignments, new app registrations, credential additions to service
principals. That's where persistence and privilege escalation show up in the cloud.

## The identity-first attacks

Each paired with what it looks like in the logs — the same discipline as the AD step.

| Attack | What it does | Signal |
|---|---|---|
| **Password spray** (T1110.003) | One password across many cloud accounts | Many 50126s from few IPs; distributed across accounts |
| **MFA fatigue / bombing** (T1621) | Spams push approvals until the user taps accept | Repeated MFA challenges then a success; user later denies it |
| **Token theft / pass-the-token** (T1550.001) | Steals an access/refresh token, replays it | Token used from a new IP, ASN, or device; session anomalies |
| **AiTM phishing** | Proxies the login to capture the *post-MFA* token | Sign-in from a proxy IP; impossible travel; new device registration right after |
| **Illicit OAuth consent** (T1528) | Tricks a user into granting an app broad permissions | Audit log: consent to an unknown app requesting mail/files scopes |
| **Service principal abuse** (T1098.001) | Adds credentials to an app to persist | Audit log: new client secret or certificate on a service principal |

<Callout type="detect">
**Illicit consent is the one juniors miss because it doesn't look like an attack.**
There's no failed login, no malware — a user simply clicks "Accept" on an app
asking for `Mail.Read` and `Files.ReadWrite.All`, and now an attacker's app has
standing access to their mailbox that survives password resets and MFA. The
detection lives entirely in the **audit log** consent events, not the sign-in
logs. Being able to describe this attack marks you out as current.
</Callout>

## Why token theft beats MFA

Worth internalising because interviewers probe it: MFA is checked when a token is
**issued**, not on every use. An attacker who steals a valid token (via AiTM
phishing, or malware reading it from a browser) replays it and is already
authenticated — the MFA prompt never re-fires because the session is considered
established. This is why the defensive frontier has moved to **token protection**,
**conditional access on device compliance**, and **shortened token lifetimes**,
rather than MFA alone. "MFA solves phishing" is a claim a good interviewer will
push on, and the correct answer is that AiTM and token theft route around it.

  step="track/01-foundations/06-cloud-identity"

  title="A sign-in from two countries in ten minutes"
  minutes={8}
>
<div slot="brief">

An impossible-travel alert lands. You pull the sign-in and audit logs for the
user:

```text
User: r.okonkwo@corp.com

Sign-in 1  08:41  London, GB       IP 82.x (corp VPN egress)
           App: Office 365        MFA: satisfied (authenticator)
           Device: compliant       Result: success

Sign-in 2  08:49  Lagos, NG        IP 105.x (hosting provider ASN)
           App: Office 365        MFA: satisfied (token)
           Device: unregistered    Result: success
           Conditional Access: "Require compliant device" — NOT applied
                                (policy scoped to Exchange only)

Audit log  08:52  Consent granted to app "Mail Backup Pro"
                  Scopes: Mail.Read, Mail.ReadWrite, offline_access
                  Consent type: user

Audit log  08:53  Inbox rule created: move messages containing
                  "invoice","payment","bank" to RSS Feeds; mark read
```

Triage it. What happened, and what's your call?

</div>
<div slot="model">

**This is an account takeover via AiTM phishing, now establishing persistence and
preparing for business email compromise.** Read the sequence:

1. **Two successful sign-ins, 8 minutes apart, London then Lagos.** Physically
   impossible, so one is not the real user. The London one — corp VPN, compliant
   device, authenticator MFA — is genuine. The Lagos one is the attacker.
2. **The Lagos sign-in "satisfied MFA" via token, from an unregistered device on a
   hosting ASN.** This is the tell for **token theft** — the attacker phished the
   user through an AiTM proxy, captured the *post-MFA* token, and replayed it. MFA
   didn't re-challenge because the token was already minted. Hosting-provider ASN
   is not where a real user in Lagos would be.
3. **Conditional Access didn't save it** — "require compliant device" existed but
   was scoped to Exchange only, so the Office 365 sign-in slipped through. That
   policy gap is a finding in its own right and worth flagging to whoever owns CA.
4. **Illicit OAuth consent to "Mail Backup Pro"** at 08:52 — the attacker grants
   their own app persistent mailbox access. This survives a password reset *and* a
   token revocation, which is why it's the most important artifact here. Killing
   the session alone won't remove it.
5. **The inbox rule** hiding invoice/payment/bank mail is classic BEC staging —
   they're hunting for a payment thread to hijack and hiding the evidence from the
   real user.

**Order:** AiTM phish → token replay from Lagos → OAuth consent for persistence →
inbox rule for BEC prep. Minutes apart, fully automated in places.

**Your call — escalate now, this is a live BEC in progress:**

- **Recommend immediate response**, and be specific that password reset is *not
  sufficient*: the session tokens must be revoked **and** the OAuth grant to "Mail
  Backup Pro" removed, or the attacker retains access. This is the detail that
  distinguishes a real answer.
- **Recommend removing the inbox rule** and reviewing what mail was already
  accessed.
- **Flag the Conditional Access gap** — the compliant-device policy scoped to
  Exchange only let this through; that's a systemic fix beyond this one incident.
- **Scope it:** was "Mail Backup Pro" consented by anyone else? A malicious app is
  rarely aimed at one user. Pivot on the app ID across the tenant.

**What would change it:** if `r.okonkwo` were genuinely travelling and using a
personal device via a Lagos hosting VPN, sign-in 2 could be benign — but the
OAuth consent and the invoice-hiding inbox rule are not explainable by travel.
Those two artifacts are what turn "possible false positive" into "confirmed
compromise", and they're why you read the audit log, not just the sign-in log.

</div>
</Scenario>
