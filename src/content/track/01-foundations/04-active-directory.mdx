<Why asked="Explain how Kerberos authentication works, then tell me what Kerberoasting is and how you'd detect it.">
Active Directory is the crown jewel of nearly every organisation you'll defend,
and it is what almost every intrusion is ultimately trying to own. A SOC that
can't reason about AD authentication is blind to the middle of every attack
chain — the part between initial access and impact. This is also where your CEH
knowledge pays off hardest, *if* you can pair each attack you already know with
the event it generates. That pairing is the whole interview.
</Why>

## What AD actually is

A directory service: a hierarchical database of objects (users, computers,
groups, organisational units) plus the authentication and authorisation that
governs them. The pieces to hold in your head:

- **Domain** — an administrative and security boundary. `corp.example.com`.
- **Domain Controller (DC)** — a server running AD DS that authenticates
  principals and holds a replica of the database (`NTDS.dit`). Compromising a DC
  is checkmate.
- **Forest** — one or more domains sharing a schema and trust. The real security
  boundary is the forest, not the domain — a distinction that matters because
  trust relationships are an attack path.
- **OU** — a container for organising objects and applying Group Policy.
- **GPO** — Group Policy Object: configuration pushed to users and computers.
  Attackers love GPOs because a single edit reaches every machine it applies to.
- **Global Catalog** — a forest-wide index, queried on TCP 3268.
- **`NTDS.dit`** — the database file holding every account's password hash. The
  ultimate loot; DCSync exists to extract from it remotely.

## NTLM — the old protocol you'll still see everywhere

NTLM is challenge-response and still ubiquitous despite Kerberos being preferred:

```text
1. Client → Server:  NEGOTIATE
2. Server → Client:  CHALLENGE (a random nonce)
3. Client → Server:  RESPONSE (nonce encrypted with the NT hash)
4. Server → DC:      validate the response
```

The security-relevant fact: **the client proves it knows the hash, never the
password.** That is the entire basis of **pass-the-hash (T1550.002)** — steal the
NT hash from LSASS and you can authenticate as that user without ever knowing or
cracking their password. NTLM has no mutual authentication and is relay-able,
which is why NTLM relay attacks exist and why modern hardening pushes hard toward
Kerberos and SMB signing.

## Kerberos — learn this cold

The most-tested protocol in blue-team interviews. Three parties: the client, the
service, and the DC acting as **Key Distribution Center (KDC)**, which has two
roles — the Authentication Service (AS) and the Ticket Granting Service (TGS).

```text
── AS Exchange (once, at logon) ──────────────────────────
1. AS-REQ   Client → KDC   "I am alice", timestamp encrypted with alice's key
2. AS-REP   KDC → Client   TGT (encrypted with the krbtgt key) + session key
                            → Event 4768 on the DC

── TGS Exchange (per service) ────────────────────────────
3. TGS-REQ  Client → KDC   TGT + "I want the CIFS service on FILE01"
4. TGS-REP  KDC → Client   Service ticket (encrypted with the service
                            account's key)
                            → Event 4769 on the DC

── AP Exchange (to the service) ──────────────────────────
5. AP-REQ   Client → Service   presents the service ticket
6. Service validates it — no call back to the DC needed
```

Two facts unlock every Kerberos attack:

- **The TGT is encrypted with the `krbtgt` account's key.** Steal that key and you
  can forge any TGT for anyone, forever — a **golden ticket (T1558.001)**. It's why
  `krbtgt` compromise means rebuilding the domain, not resetting a password.
- **A service ticket is encrypted with the service account's key**, which is derived
  from that account's password. Request one and you can crack it offline — that's
  Kerberoasting.

<Callout type="key">
Interview-ready Kerberos, compressed: *"The client gets a TGT from the AS, proving
its identity once. It presents that TGT to the TGS to get service tickets for
specific services. The service validates the ticket itself using its own key,
without contacting the DC. The DC logs 4768 for the TGT and 4769 for each
service ticket — which is exactly where the detections live."*
</Callout>

## The attacks, each paired with its telemetry

This table is the point of the whole step. You know the left column from CEH.
The right column is what gets you hired.

| Attack | What it does | Detection |
|---|---|---|
| **Kerberoasting** (T1558.003) | Requests service tickets for SPN accounts, cracks them offline | 4769 with encryption type 0x17 (RC4) for service accounts; one principal requesting many SPNs |
| **AS-REP Roasting** (T1558.004) | Targets accounts with pre-auth disabled; crackable AS-REP | 4768 with pre-auth type 0; enumerate accounts with `DONT_REQ_PREAUTH` |
| **Pass-the-Hash** (T1550.002) | Authenticates with a stolen NT hash | 4624 type 3 with NTLM where Kerberos is expected; LSASS access preceding it |
| **Pass-the-Ticket** | Injects a stolen Kerberos ticket | Ticket use from an unexpected host; 4768/4769 anomalies |
| **Golden Ticket** (T1558.001) | Forged TGT using the krbtgt key | 4769 with no preceding 4768; anomalous ticket lifetimes; username mismatches |
| **DCSync** (T1003.006) | Impersonates a DC to pull hashes via replication | 4662 with replication GUIDs from a non-DC host — the classic tell |
| **DCShadow** (T1207) | Registers a rogue DC to push malicious changes | Unexpected DC registration; replication from an unknown source |

<Callout type="detect">
The single highest-value AD detection to be able to describe: **DCSync from a
non-DC.** Event 4662 records directory access; a replication request
(the `DS-Replication-Get-Changes` GUID) should only ever come from an actual
domain controller. Seeing it from a workstation means someone is pulling the
entire domain's hashes. Say this in an interview and you sound like you've worked
a real environment.
</Callout>

<Scenario
  step="track/01-foundations/04-active-directory"
  id="kerberoast"
  title="4769 activity from a single workstation"
  minutes={8}
>
<div slot="brief">

A scheduled hunt surfaces this and routes it to you:

```text
Source host:   WKSTN-2210  (user: t.abara)
Time window:   14:02:11 – 14:02:40  (29 seconds)
Event ID:      4769  ×  14
Service names: MSSQLSvc/db01.corp.local:1433
               MSSQLSvc/db02.corp.local:1433
               HTTP/intranet.corp.local
               CIFS/fileserver.corp.local
               ... (14 distinct service accounts total)
Ticket Encryption Type:  0x17  (RC4-HMAC)  on all 14
Failure code:  0x0  (success)

Context: the domain's default is AES; RC4 is deprecated but still permitted.
No 4768 anomalies. t.abara is a standard marketing user.
```

Triage this. What is it, how confident are you, and what do you do?

</div>
<div slot="model">

**This is Kerberoasting (T1558.003), and the confidence is high.** Three
independent signals agree:

1. **One principal requesting many distinct service tickets in seconds.** A normal
   user acquires service tickets as they access services, spread across a day. A
   burst of 14 in 29 seconds is programmatic enumeration of SPN accounts.
2. **RC4 (0x17) on every ticket in an AES domain.** This is the strongest single
   indicator. Kerberoasting tools deliberately request RC4 because it's faster to
   crack offline than AES. In an environment that defaults to AES, RC4 service
   tickets are the anomaly you build the detection on.
3. **The requesting user has no business reason.** A marketing user has no
   legitimate need for tickets to SQL, intranet and file services in one burst.

**What the attacker is doing:** they've compromised `t.abara`'s session (or are
running as them), enumerated accounts with SPNs, and requested a service ticket
for each. Every ticket is encrypted with that service account's password hash, so
they can now crack them offline — no further network noise, no lockouts, nothing
else to detect. Service accounts often have weak, non-expiring passwords, which
is precisely why this attack is worth their time.

**What you check:**

1. How did `t.abara`'s session get here? Pull the process tree and recent logons
   on WKSTN-2210 — this user is very likely compromised, not malicious.
2. Which of the 14 accounts are high-privilege? A Kerberoastable account that is
   also a Domain Admin is a domain-takeover path. Prioritise those.
3. Any subsequent successful authentication as one of those service accounts? If
   a crack has already succeeded, you'll see it as new logons.

**Escalation: yes, promptly.** The cracking happens offline and invisibly, so the
window to act is now, before a service account is compromised. Escalate with the
list of targeted accounts flagged by privilege, and recommend the service-account
passwords be rotated and, where possible, moved to group Managed Service Accounts
with long random passwords.

**What would lower confidence:** a security tool or vulnerability scanner
legitimately enumerating SPNs on a schedule, from a known scanning host, would
produce a similar pattern. But this is from a marketing user's workstation, not a
scanner, so that exculpatory reading doesn't hold. Check the source-host baseline
to be sure — after escalating.

</div>
</Scenario>
