<Why asked="Most traffic is encrypted now. What can you still detect at the network layer?">
Endpoint telemetry can be tampered with by an attacker who owns the endpoint;
network telemetry usually cannot, because it is collected elsewhere. That makes it
the independent witness, and it is why network evidence carries disproportionate
weight in an investigation. The encryption question above is a favourite because
it separates candidates who think TLS ended network monitoring from those who can
list six things still visible in an encrypted session.
</Why>

## What you actually work with

Full packet capture is expensive and rarely available beyond a short buffer. Most
SOCs work with **Zeek logs** (or equivalent), which summarise every connection
into structured records:

| Log | Contains |
|---|---|
| `conn.log` | Every connection: endpoints, ports, duration, bytes each way, state |
| `dns.log` | Query, type, response, return code |
| `http.log` | Method, host, URI, user-agent, status, response size |
| `ssl.log` | SNI, TLS version, cipher, certificate subject and issuer, JA3 |
| `files.log` | Files seen traversing the network, with hashes |
| `notice.log` | Zeek's own detections |

`conn.log` alone answers most triage questions. The fields that matter most:
`duration`, `orig_bytes`, `resp_bytes`, and `conn_state`.

<Callout type="key">
The byte ratio is one of the most useful single signals in network triage. Normal
web browsing sends a little and receives a lot - a low `orig_bytes` to high
`resp_bytes` ratio. **Exfiltration inverts it.** A host sending far more than it
receives, sustained, is worth investigating regardless of the destination's
reputation.
</Callout>

## Beaconing

Malware checks in on a schedule. Humans do not. That difference is detectable
without decrypting anything:

- **Regular intervals** with low variance. Compute the gaps between connections
  from one host to one destination, then the coefficient of variation (standard
  deviation over mean). Human traffic is bursty and irregular; a beacon sleeping
  60 seconds is near-constant.
- **Consistent small payloads.** Check-ins that carry no tasking are near-identical
  in size.
- **Long-lived, low-volume relationships.** Days of contact, very little data.
- **Activity outside working hours**, continuing when the user is not present.

Modern C2 frameworks add **jitter** - randomising the sleep by a percentage -
specifically to defeat this. So real detections use a wider tolerance and accept
more false positives, and you must be ready to say so rather than presenting
beaconing detection as a solved problem.

**The reliable false positive sources:** software update checks, telemetry
agents, monitoring tools, NTP, and certificate revocation checking. These are the
most regular traffic on any network, which is precisely why tuning matters here.

## DNS as a covert channel

You met the theory in Phase 1. Applied:

- **Tunnelling (T1071.004)** - data encoded in subdomain labels. Signals: unusually
  long labels, high character entropy, high query volume to one registrable domain,
  TXT or NULL record types from hosts with no reason to use them, and low or zero
  cache-hit behaviour because every query must be unique.
- **DGA (T1568.002)** - bursts of NXDOMAIN as malware hunts for a live C2 domain.
- **DNS over HTTPS** - if endpoints resolve via DoH to an external provider, your
  DNS visibility disappears entirely. Detecting and blocking unauthorised DoH is
  itself a control worth naming.

## What TLS does and does not hide

The interview question. Encrypted payloads, yes - but a great deal remains:

1. **SNI** - the hostname, in cleartext in the Client Hello. Encrypted Client Hello
   closes this, but adoption is partial.
2. **Certificate details** - subject, issuer, validity dates. Self-signed
   certificates, or default framework certificates, are a real signal.
3. **JA3 / JA4 fingerprints** - a hash of how the client negotiates TLS. Different
   client libraries produce different fingerprints, so a fingerprint that does not
   match any legitimate software on your estate is suspicious even when the
   destination looks fine.
4. **Metadata** - who talked to whom, when, for how long, how many bytes each way.
5. **Timing and volume patterns** - beaconing, as above.
6. **The destination itself** - IP, ASN, domain age, reputation.

<Callout type="warn">
Do not oversell JA3. It is a strong signal, not proof: fingerprints collide across
software using the same TLS library, and JA3 can be deliberately mimicked. JA4
improved on it. Presenting it as a reliable identifier is the trap; presenting it
as a strong correlation signal is correct.
</Callout>

  SNI:          cdn-metrics.io

  JA3:          51c64c77e60f3980eea90869b68c58a8

  cdn-metrics.io          A     104.21.x.x    (first seen 8 days ago)

  b8e1d5a2f6c3.telemetry-sync.net   TXT   NXDOMAIN
  ... 1,412 similar queries over 7 days, all unique subdomains

  - JA3 51c64c... does not match any approved software baseline.
  - No other host on the estate contacts cdn-metrics.io.
  - The 185.199.x.x transfer occurred at 02:14 on day 6.

Identify every finding, rank them, and state your conclusion.

</div>
<div slot="model">

**This host is compromised. There are three distinct findings and they form a
complete attack narrative: C2, a covert channel, and exfiltration.**

**Finding 1 - C2 beaconing to `cdn-metrics.io` (highest confidence).**

- 9,847 connections with a mean gap of 61.2 seconds and a standard deviation of
  4.1 gives a jitter coefficient of about 0.067. That is machine-regular. Human
  traffic never looks like this.
- **Near-symmetric byte counts** (412 KB out, 398 KB in) across nearly ten thousand
  connections is check-in traffic carrying little tasking - completely unlike web
  browsing, which is heavily asymmetric toward inbound.
- **Self-signed certificate issued nine days ago**, with the domain first resolved
  eight days ago. Fresh infrastructure stood up immediately before use.
- **JA3 matches no approved software**, and **no other host contacts this domain**.
  A legitimate service used by one machine on the estate is close to a
  contradiction in terms.

Every one of those is individually suggestive; together they are conclusive.

**Finding 2 - DNS tunnelling to `telemetry-sync.net` (high confidence).**

1,412 unique high-entropy subdomains, all TXT queries, all returning NXDOMAIN.
This is a covert channel: the data is in the query name, so the response does not
matter - which is exactly why NXDOMAIN is expected rather than a sign of failure.
TXT queries from a marketing workstation have no legitimate explanation. Note this
is a *second* channel, distinct from finding 1, which suggests either a backup C2
or a deliberately separated exfiltration path.

**Finding 3 - bulk exfiltration (high confidence, highest impact).**

Three connections, **1.9 GB outbound against 41 KB inbound**, at 02:14 to a cloud
storage provider. The inverted byte ratio is the signal, and the volume plus the
hour makes it unambiguous. This is T1041 / T1567 - the data leaving.

**The Windows Update entry is a deliberate control.** 840 MB inbound against 2.1 MB
outbound, variable intervals, to a known Microsoft endpoint - normal patching, and
included so that "large transfer" alone is not treated as the signal. **Direction
and regularity are what matter, not volume.**

**Ranking for response:** finding 3 first, because data has already left and the
scoping question - what was taken - drives regulatory and customer obligations.
Then finding 1, because it is the live control channel and cutting it stops
further activity. Then finding 2, as a second channel that must also be closed or
the attacker retains access.

**Conclusion and actions:**

- **Escalate immediately as a confirmed compromise with data exfiltration.** The
  exfiltration element materially changes the incident class - this is potentially
  a notifiable data breach, and that determination has a clock on it.
- **Recommend containment:** isolate WKSTN-2210, preserving memory. Block both
  domains and the storage destination at the perimeter.
- **Scope urgently:** what did that host have access to, and what was in the 1.9 GB?
  Check file share access logs and any DLP telemetry for the hours before 02:14.
- **Hunt the estate** for the JA3 fingerprint, both domains, and the beaconing
  pattern. One host contacting unique infrastructure is unusual enough that I would
  want to be certain it is genuinely one host.
- **Revisit the endpoint alert closed as inconclusive last week.** That was almost
  certainly the initial access, and reopening it with this context will identify
  the entry vector.

**The lesson worth carrying:** the endpoint alert alone was inconclusive; the
network view made it obvious. Neither telemetry source is sufficient, and the
network view is the harder one for an attacker to tamper with.

</div>
</Scenario>
