<Why asked="You get an EDR alert on a suspicious process. Walk me through your triage.">
Phase 1 taught you what a normal process tree looks like. This step is the applied
version, and it deliberately includes the harder half of the job: correctly
concluding that something suspicious is benign. Anyone can escalate a clearly
malicious tree. The analyst who gets promoted is the one who can clear a
frightening-looking alert with documented reasoning, and who knows exactly what
evidence would have changed their mind.
</Why>

## The triage sequence

Work it in this order every time. The consistency matters more than the speed.

1. **What fired, and why?** Read the detection logic. A rule matching a filename
   and a rule matching LSASS access deserve very different starting confidence.
2. **The process tree, upward.** The parent chain tells you how this got here.
   Almost every conclusion starts here.
3. **The command line.** Decoded, in full. This is usually where intent lives.
4. **The binary.** Path, signature, hash, prevalence. Is it where it should be?
5. **What it did next.** Children, file writes, registry changes, network
   connections.
6. **Context.** Whose machine, what is their role, what were they doing, is there a
   change window.
7. **Scope.** Has this pattern appeared anywhere else in the estate?

<Callout type="key">
Step 6 is the one juniors skip and it resolves more alerts than any other. A
PowerShell download cradle on a developer's machine during working hours with a
matching change ticket is a different event from the same command on a
receptionist's laptop at 03:00. Context is not an excuse for a weak conclusion; it
is evidence.
</Callout>

## Decoding what you find

**Base64 PowerShell.** Decode it rather than describing it as "encoded":

```powershell
[Text.Encoding]::Unicode.GetString([Convert]::FromBase64String('SQBFAFgA...'))
```

Windows PowerShell uses UTF-16LE for `-EncodedCommand`, which is why `Unicode` is
the right encoding and why a naive base64 decode produces text with null bytes
between characters. Knowing that detail is a small, credible signal.

**Flags that signal intent:** `-nop` (skip profile), `-w hidden` (hide window),
`-ep bypass` (ignore execution policy), `-enc` (base64), `-noni`
(non-interactive), `IEX` / `Invoke-Expression` (execute a string), `DownloadString`
and `DownloadFile` (fetch remote code). Any one may be innocent. Four together are
not.

## LOLBins

Signed Microsoft binaries abused to do an attacker's work, defeating naive "is it
signed?" logic. The ones to recognise instantly:

| Binary | Legitimate purpose | Abused for |
|---|---|---|
| `rundll32.exe` | Run a DLL export | Executing payloads, proxying execution |
| `regsvr32.exe` | Register a DLL | Remote scriptlet execution (Squiblydoo) |
| `mshta.exe` | Run HTML applications | Executing remote HTA payloads |
| `certutil.exe` | Certificate utility | Downloading files, base64 decode |
| `bitsadmin.exe` | Background transfers | Stealthy download and persistence |
| `msiexec.exe` | Install MSI packages | Installing remote MSI payloads |
| `wmic.exe` | WMI command line | Remote execution, discovery |
| `installutil.exe` | .NET installer | Bypassing application control |

The triage question is never "is this binary bad" — they are all legitimate. It is
**"is this binary doing its actual job, invoked by a plausible parent, with
arguments that make sense?"** `certutil` fetching a `.exe` over HTTP is not
certificate management.

## Persistence hunting

When you have confirmed something ran, check whether it arranged to run again:

- Registry Run keys, machine and user
- Services (7045, 4697)
- Scheduled tasks (4698, and Sysmon 1 with `schtasks.exe`)
- WMI event subscriptions (Sysmon 19, 20, 21) - the quiet one people miss
- Startup folders
- Winlogon `Userinit` and `Shell` values

<Callout type="warn">
Missing persistence is how an incident recurs a week later with someone asking why
it was closed. If you confirm execution, persistence hunting is not optional, and
saying so unprompted in an interview is a strong signal.
</Callout>

  minutes={10}

<div slot="brief">

An EDR alert fires. This one is genuinely ambiguous, which is the point.

```text
ALERT: "LOLBin abuse - certutil remote download"  Severity: High

Process:      certutil.exe  (PID 7742)
Path:         C:\Windows\System32\certutil.exe   (signed, Microsoft)
CommandLine:  certutil.exe -urlcache -split -f
              http://10.44.2.19/pkg/agent-installer.msi
              C:\Windows\Temp\agent-installer.msi
Parent:       cmd.exe (PID 7738)
Grandparent:  ccmexec.exe (PID 1204)
User:         NT AUTHORITY\SYSTEM
Host:         WKSTN-3391
Time:         Wed 11:14:22 (business hours)

FOLLOW-ON ACTIVITY
  Sysmon 11  C:\Windows\Temp\agent-installer.msi created
  Sysmon 1   msiexec.exe /i C:\Windows\Temp\agent-installer.msi /qn
             parent: cmd.exe (7738)
  Sysmon 3   none outbound except the 10.44.2.19 fetch
  No LSASS access. No registry Run key changes. No new services
  beyond the MSI's own.

CONTEXT
  - 10.44.2.19 resolves to sccm-dp02.corp.local (internal
    distribution point), confirmed in asset inventory.
  - The same command ran on 217 other workstations in a 40-minute
    window this morning.
  - Change ticket CHG-4471 "Deploy monitoring agent v4.2" is open,
    scheduled for today.
  - The MSI hash matches the vendor's published hash.
```

What is your conclusion, and what would have changed it?

</div>
<div slot="model">

**Conclusion: benign. This is software deployment via SCCM, and I would close it
as a true negative with a tuning recommendation.**

The alert is not wrong to have fired - `certutil -urlcache -split -f` is a
genuine download cradle and a well-known LOLBin technique (T1105). The skill here
is not pattern-matching the command to "malicious"; it is weighing the full
context and being willing to reach a confident negative conclusion.

**The evidence supporting benign, in order of weight:**

1. **The grandparent is `ccmexec.exe`** - the SCCM client agent. That is a
   legitimate software deployment chain, and it explains both the SYSTEM context
   and the `cmd.exe` intermediary.
2. **The source is an internal, inventoried distribution point.** Not an external
   IP, not a hosting provider, not a domain registered last week. Confirmed against
   asset inventory rather than assumed from the RFC1918 range.
3. **Fleet-wide identical execution.** 218 hosts in 40 minutes is deployment
   behaviour. Targeted attacks do not look like this; worm-like propagation could,
   but that would show lateral movement telemetry, which is absent.
4. **A matching change ticket.** Correlating to CHG-4471 is the step that converts
   a plausible story into a verified one.
5. **The MSI hash matches the vendor's published hash.** The payload is what it
   claims to be.
6. **No post-execution indicators.** No credential access, no persistence beyond
   what the MSI legitimately installs, no outbound connections, no discovery
   commands. A real intrusion using certutil would almost certainly do something
   next.

**What would have changed my conclusion - any one of these:**

- **The source IP not matching a known internal asset**, or resolving externally.
  An RFC1918 address is not automatically trustworthy; an attacker with a foothold
  hosts payloads internally precisely because it looks like this.
- **A parent chain that did not include a legitimate deployment agent.** The same
  certutil command parented to `winword.exe`, `explorer.exe` or a browser is
  malicious until proven otherwise.
- **Execution on one host rather than hundreds**, or on an odd subset such as only
  the finance team.
- **No corresponding change ticket**, or a ticket that does not match the payload.
- **A hash mismatch**, or a payload that no vendor claims.
- **Any follow-on indicator**: LSASS access, a Run key write, a scheduled task, an
  outbound connection to anything unexpected, or discovery commands.
- **Timing outside a change window**, particularly overnight.

**What I do with it:**

- Close as benign, and **document all of the above**. A closure that says
  "legitimate SCCM deployment" without the evidence is only marginally better than
  "closed, FP" - the next analyst needs to be able to verify the reasoning rather
  than trust it.
- **Raise a tuning request**, scoped correctly: suppress `certutil` download
  activity where the parent chain includes `ccmexec.exe` **and** the destination is
  a known distribution point. Not "suppress certutil", and not "suppress on this
  host" - both would hand an attacker a free channel, since SCCM is an attractive
  target exactly because it can execute everywhere.
- **Note the underlying weakness for the customer**: using `certutil` as a
  downloader in deployment tooling is poor practice, because it forces defenders to
  allowlist a technique attackers rely on. Recommending the deployment be changed
  removes the ambiguity permanently. That is fixing the environment rather than the
  detection, and it is the better fix where it is available.

**The transferable lesson:** a confident, well-documented negative is as valuable
as an escalation and considerably harder. The test of your reasoning is not
whether you reached the right answer - it is whether you can state precisely what
would have made you reach the other one.

</div>
</Scenario>
