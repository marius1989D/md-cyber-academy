<Why asked="How would you decide what to log?">
Every detection you will ever write is downstream of a collection decision
somebody made, often years earlier and usually on cost grounds. Analysts who
don't understand the pipeline blame the SIEM when a query returns nothing;
analysts who do understand it can say *"we don't have that telemetry, here's what
we'd need to collect and roughly what it would cost."* That second sentence is a
Tier 2 sentence, and saying it in a Tier 1 interview is how you get hired above
your level.
</Why>

## The pipeline, end to end

```text
  SOURCES          COLLECTION       PROCESSING        STORAGE        USE
  ────────         ──────────       ──────────        ───────        ───
  Endpoints  ──┐                                    ┌─ Hot  7-90d ──┬─ Detections
  Network    ──┤   Agent      ──▶  Parse       ──▶  ├─ Warm  90-365d┼─ Hunting
  Identity   ──┼─▶ Syslog     ──▶  Normalise   ──▶  ├─ Cold  1-7yr  ┼─ Investigation
  Cloud/SaaS ──┤   API poll   ──▶  Enrich      ──▶  └───────────────┴─ Compliance
  Apps       ──┘   Forwarder       Filter/route
```

Every stage is a place things silently break, and knowing where to look when a
query returns nothing is a real diagnostic skill:

- **Source** — is the log even generated? Windows command-line auditing is off by
  default; you learned that in Phase 1. Many applications log nothing useful
  unless configured to.
- **Collection** — is the agent installed, running, and actually shipping? Agent
  health monitoring is unglamorous and is the single most common cause of a
  detection blind spot.
- **Processing** — did the parser understand the format? A vendor changes their log
  format in an update and fields silently become null. Detections keep running and
  keep finding nothing.
- **Storage** — is the data still in the tier you're querying? Searching 90 days
  back when hot retention is 30 returns an empty result, not an error.

<Callout type="warn">
**Empty results and broken pipelines look identical.** A query that returns
nothing might mean "no attack" or "no data". Before concluding a host is clean,
confirm you're actually receiving its telemetry — check the last heartbeat, or run
a query for *any* event from that host in the window. Analysts who skip this
declare things clean that were never being watched.
</Callout>

## Collection methods, and what breaks each

| Method | How | Fails when |
|---|---|---|
| **Agent** | Software on the host forwards logs (AMA, Splunk UF, Elastic Agent, Wazuh) | Agent stops, host offline, version drift, config not applied |
| **Agentless / WEF** | Windows Event Forwarding to a collector | Subscription misconfigured, WinRM broken, GPO not applied |
| **Syslog** | Network devices push UDP/TCP 514 to a collector | UDP is lossy and silent; collector overload drops events |
| **API polling** | SIEM pulls from a cloud provider on a schedule | Rate limits, token expiry, polling gaps, API changes |
| **Flow / packet** | NetFlow, or full pcap via a TAP or SPAN | Sampling loses detail; encryption limits payload value; storage cost |

<Callout type="key">
Syslog over **UDP** has no delivery guarantee. If the collector is busy or the
network drops a packet, that event is simply gone and nothing anywhere records
that it was lost. When an interviewer asks about logging reliability, "I'd prefer
TCP syslog, or better an agent with local buffering, because UDP syslog fails
silently" is a strong, specific answer.
</Callout>

## Normalisation — why field names matter

Every source names things differently. A source IP might arrive as `src_ip`,
`SourceIp`, `ipAddress`, `client_addr` or `c-ip`. Normalisation maps them to a
common schema so one query can span sources.

The schemas you should know by name:

- **ASIM** — Advanced Security Information Model, Microsoft Sentinel's schema.
- **ECS** — Elastic Common Schema.
- **CIM** — Common Information Model, Splunk's.
- **OCSF** — Open Cybersecurity Schema Framework, the vendor-neutral effort.

The practical consequence: **a detection written against normalised fields
survives a source change; one written against raw vendor fields breaks.** That is
the same durability argument you'll meet again in the Pyramid of Pain, applied to
schemas instead of indicators.

## Enrichment

Adding context at ingest so the analyst doesn't have to look it up during triage:

- **Geo-IP and ASN** — turns an IP into "hosting provider in Lithuania"
- **Threat intel matching** — flags known-bad indicators
- **Asset context** — is this a domain controller or a print server? Criticality
  changes severity
- **Identity context** — department, manager, privileged or not
- **DNS resolution** — hostname alongside IP

Good enrichment is the difference between a five-minute triage and a
twenty-minute one, across hundreds of alerts a day. It is one of the highest-ROI
things a SOC can invest in and one of the most commonly neglected.

## Retention, cost and the real trade-off

Retention tiers exist because SIEM licensing is usually priced on ingest volume,
storage or both:

- **Hot** — fast, searchable, expensive. Typically 30–90 days.
- **Warm / archive** — cheaper, slower to search. 90 days to a year.
- **Cold** — cheapest, may need restoring before it's searchable. Often years,
  driven by compliance rather than security.

The security problem: **dwell time frequently exceeds hot retention.** If an
intrusion started 120 days ago and you keep 90 days hot, the initial access
evidence is gone or expensive to retrieve — exactly when you most need it, during
a major incident.

**How you decide what to log**, which is the interview question:

1. Start from the threats and techniques that actually matter to this
   organisation, not from a vendor's list.
2. Use ATT&CK **Data Sources** to determine what telemetry those techniques need.
3. Rank by detection value per gigabyte. Windows security events and Sysmon 1/3/22
   are enormously valuable per byte; verbose DEBUG application logs usually are not.
4. Collect selectively at the source, filter at the collector, and let the noisy
   but occasionally-useful data go to cheap archive rather than hot storage.
5. Measure the result. Which log sources have ever contributed to a real
   detection? Sources that have never contributed to anything are a budget you
   could spend on ones that would.

<div slot="brief">

You've joined an MSSP and are reviewing a new customer's onboarding document
before their first month of monitoring.

```text
CUSTOMER: Meridian Logistics · 850 staff · Microsoft 365 + on-prem AD
                                · 3 public web apps · 40 servers

LOG SOURCES CONNECTED
  ✓ Entra ID sign-in logs                    hot 90d
  ✓ Microsoft Defender for Endpoint alerts   hot 90d
  ✓ Firewall (Palo Alto) traffic logs        hot 30d  · UDP syslog
  ✓ Windows Security event log — DCs only    hot 90d
  ✓ Email security gateway                   hot 90d

NOT CONNECTED
  ✗ Entra ID audit logs
  ✗ Windows Security events — member servers & workstations
  ✗ Sysmon — not deployed anywhere
  ✗ Web application / IIS logs
  ✗ DNS query logs

NOTES
  · Defender is licensed P2 across the estate
  · "Command line auditing not enabled — was flagged as noisy in 2023"
  · Average dwell time in this sector reported at ~180 days
```

Name the three most serious gaps in priority order, say what each one blinds you
to, and give one that is cheap to fix.

</div>
<div slot="model">

**Gap 1 — Entra ID audit logs are missing.** This is the most serious, and it's
the one most people skip because sign-in logs are connected and look sufficient.
They are not the same log. The audit log is where **OAuth consent grants, inbox
rule creation, role assignments, MFA method changes and service principal
credential additions** are recorded. Everything you learned in the cloud identity
step about illicit consent and BEC persistence is invisible here. This customer
is Microsoft 365-based with 850 staff — BEC is the single most likely incident
they will actually experience, and you cannot detect its persistence mechanisms
at all. **It is also free to enable and low volume.** Highest impact, lowest cost:
fix it first.

**Gap 2 — endpoint telemetry is alerts-only.** Defender is sending *alerts* but no
raw Windows Security events from workstations and member servers, and no Sysmon
anywhere. That means you can see what Defender chose to flag, and nothing else.
You cannot investigate around an alert, cannot hunt, cannot build custom
detections, and cannot reconstruct a process tree — every one of the Phase 1
scenarios becomes impossible. Worse, they hold **Defender P2**, which includes
advanced hunting tables. That licence is already paid for and unused, so
connecting the Defender advanced hunting data is a configuration change, not a
purchase. The "command line auditing is noisy" note from 2023 should be
revisited — 4688 without command lines is close to useless, and this is the
single most valuable field in endpoint telemetry.

**Gap 3 — 30-day firewall retention against ~180-day dwell time.** By the time this
customer discovers an intrusion, the network evidence of initial access will be
six months gone. Compounding it, the firewall arrives over **UDP syslog**, which
drops events silently under load — so you don't even know how complete the 30 days
you *do* have actually is. Two fixes: move firewall logs to archive tier beyond 30
days rather than deleting them, and move the transport to TCP.

**Cheapest fix:** Entra ID audit logs. It's a toggle in the data connector, the
volume is small, and it closes the gap most likely to matter for this customer's
actual threat profile.

**The honourable mentions:** no DNS logs means no DNS tunnelling or DGA detection —
covered partly if Sysmon 22 is deployed later, which is another argument for
Sysmon. No web/IIS logs with three public web apps means web attacks and webshells
are entirely invisible, which for an internet-facing estate is a serious gap in
its own right.

**How to raise it:** frame gaps in terms of *what incident you would fail to
detect*, not in terms of missing data sources. "We cannot detect mailbox
persistence after an account takeover" lands with a customer. "You haven't
connected the audit log" does not.

</div>
