<Why asked="You've written all your detections in KQL. What happens when you join a company running Splunk?">
Sigma is the answer to that question, and it is a fair one to be asked - the UK
market is Microsoft-heavy but not exclusively so, and an analyst whose skills are
welded to one vendor is a narrower hire. Learning Sigma converts your detection
work from a Sentinel skill into a detection engineering skill. It also gives you
the single most credible portfolio item available at entry level: a rule accepted
into a public repository that working analysts actually use.
</Why>

## What Sigma is

A YAML format for describing detections independently of any SIEM, plus a
converter that translates a rule into the query language of whatever backend you
target - KQL, SPL, Elastic DSL, and dozens more.

**Write once, convert anywhere.** The value is not just portability between jobs -
it is that the community writes rules in a shared format, so a Sigma repository is
thousands of peer-reviewed detections you can convert straight into your own
environment.

## Anatomy of a rule

```yaml
title: Rundll32 Execution With Script Protocol Handler
id: 8b1e5f0c-9a3d-4e7b-b2c1-6d4f8a9e0c3b
status: experimental
description: >
    Detects rundll32.exe invoked with a script protocol handler such as
    javascript: or vbscript:, a common proxy execution technique used to
    run code through a signed Microsoft binary.
references:
    - https://attack.mitre.org/techniques/T1218/011/
    - https://lolbas-project.github.io/lolbas/Binaries/Rundll32/
author: Marius Dumitru
date: 2026/07/25
tags:
    - attack.defense-evasion
    - attack.t1218.011
logsource:
    category: process_creation
    product: windows
detection:
    selection_img:
        - Image|endswith: '\rundll32.exe'
        - OriginalFileName: 'RUNDLL32.EXE'
    selection_cli:
        CommandLine|contains:
            - 'javascript:'
            - 'vbscript:'
            - 'RunHTMLApplication'
    filter_optional_legitimate:
        ParentImage|endswith: '\ccmexec.exe'
        CommandLine|contains: 'inventory'
    condition: all of selection_* and not 1 of filter_optional_*
falsepositives:
    - Rare legitimate software using script protocol handlers through
      rundll32, typically deployment or inventory tooling
level: high
```

The fields that matter most:

- **`logsource`** - the abstraction that makes portability work. `category:
  process_creation` maps to `DeviceProcessEvents` in Defender, `SecurityEvent`
  with EventID 4688 in Sentinel, `Sysmon EventCode=1` in Splunk. You describe the
  kind of data, the converter handles the table names.
- **`detection`** - named selection blocks and filter blocks, combined by
  `condition`. Naming blocks `selection_*` and `filter_*` lets you write
  `all of selection_*` and `not 1 of filter_*`, which is the idiomatic style.
- **Field modifiers** - `|contains`, `|endswith`, `|startswith`, `|re`, `|base64`,
  `|all`. These are where the expressiveness lives.
- **`falsepositives`** - **a required field.** The format itself insists you
  document expected noise, which is the Phase 2 tuning discipline baked into the
  specification.
- **`level`** - informational, low, medium, high, critical.

<Callout type="key">
The `falsepositives` field being mandatory is a genuinely interesting design
decision to mention in an interview. The industry standard format treats
"what benign activity will trigger this?" as part of writing a rule, not an
afterthought - which is exactly the argument you learned in Phase 2.
</Callout>

## Converting

`sigma-cli` with pySigma backends does the translation:

```bash
pip install sigma-cli
sigma plugin install microsoft365defender
sigma plugin install splunk

# Convert one rule to Defender KQL
sigma convert -t microsoft365defender rules/rundll32_script_protocol.yml

# Convert a whole directory to Splunk
sigma convert -t splunk -f savedsearches rules/

# Check what a pipeline does to field names
sigma convert -t microsoft365defender -p microsoft365defender rules/ --verbose
```

**Pipelines** handle the field-name mapping between the generic Sigma schema and a
specific product's fields - `Image` becomes `FolderPath` or `NewProcessName`
depending on target. When a conversion produces something that looks wrong, the
pipeline is usually where to look.

<Callout type="warn">
**Always test the converted query, never assume it.** Conversion is mechanical and
correct conversions can still be semantically wrong for your environment - a field
your logsource assumes may not be collected, or may be populated differently.
Convert, run it, and validate against your atomics exactly as in the previous
step.
</Callout>

## Challenge - write a Sigma rule

<QueryChallenge
  step="track/05-lab/04-sigma"
  id="sigma-lsass"
  title="LSASS access, portably"
  lang="sigma"
  tables={["logsource: category=process_access, product=windows", "Sysmon EventID 10", "SourceImage", "TargetImage", "GrantedAccess", "CallTrace"]}
>
<div slot="brief">

Write a Sigma rule detecting **credential dumping via LSASS memory access
(T1003.001)**, aimed high on the Pyramid of Pain - it should key on the access
itself, not on tool names.

Include a filter for legitimate security tooling, and complete the
`falsepositives` field properly.

</div>
<div slot="solution">

```yaml
title: LSASS Memory Access With Suspicious Granted Access Mask
id: 3c7e9a41-2b8d-4f6a-9e1c-5a0b7d3f8e2c
status: experimental
description: >
    Detects a process opening a handle to lsass.exe with an access mask
    granting memory read, which is required by credential dumping tools
    regardless of implementation. Keys on the behaviour rather than on
    tool names, so it survives renaming and reimplementation.
references:
    - https://attack.mitre.org/techniques/T1003/001/
author: Marius Dumitru
date: 2026/07/25
tags:
    - attack.credential-access
    - attack.t1003.001
logsource:
    category: process_access
    product: windows
detection:
    selection_target:
        TargetImage|endswith: '\lsass.exe'
    selection_access:
        GrantedAccess:
            - '0x1010'
            - '0x1410'
            - '0x1438'
            - '0x143a'
            - '0x1418'
    filter_main_av:
        SourceImage|startswith:
            - 'C:\Program Files\Windows Defender\'
            - 'C:\ProgramData\Microsoft\Windows Defender\'
    filter_main_system:
        SourceImage|endswith:
            - '\wininit.exe'
            - '\csrss.exe'
            - '\services.exe'
    filter_optional_backup:
        SourceImage|endswith: '\vssvc.exe'
    condition: all of selection_* and not 1 of filter_*
falsepositives:
    - Endpoint detection and response agents legitimately reading LSASS
      memory for credential-theft protection
    - Backup and volume shadow copy services
    - Some enterprise password management and SSO agents
    - Vulnerability scanners performing authenticated credential checks
level: high
```

**Why this shape:**

- **`GrantedAccess` values are the durable signal.** `0x1010` combines
  `PROCESS_QUERY_INFORMATION` and `PROCESS_VM_READ` - what a dumper needs. Listing
  several observed masks rather than one catches variations across tools without
  naming any of them.
- **No tool names anywhere.** That is deliberate and is what puts this near the top
  of the pyramid. Renaming `mimikatz.exe` does nothing to it.
- **Filters use `SourceImage|startswith` with full paths for the AV case.** Matching
  on filename alone would let an attacker place a binary with that name elsewhere
  and inherit the exclusion - the narrow-intervention principle from Phase 2,
  expressed in Sigma.
- **`filter_main_` versus `filter_optional_`** is the community convention: main
  filters are always applied, optional ones are environment-specific and may be
  removed. The `condition` here applies both, which you would adjust per
  environment.
- **`falsepositives` is genuinely completed**, with four realistic entries. A rule
  submitted with "unknown" in that field will not be accepted upstream, and rightly
  so.

**Common wrong shapes:** including `SourceImage|endswith: '\mimikatz.exe'` in the
selection, which drops the rule to the bottom of the pyramid; filtering EDR by
filename rather than full path; omitting `CallTrace` refinements that mature
versions of this rule use to reduce noise further; and leaving `falsepositives` as
a placeholder.

**Validate it** by converting to your backend, running it, and firing the
T1003.001 atomics. Then check what your EDR does - if your filter is too broad you
will find the rule never fires at all.

</div>
</QueryChallenge>

## Contributing upstream

This is the portfolio move. SigmaHQ accepts community rules via pull request, and
a merged rule is public, permanent, peer-reviewed evidence of your work.

**How to give yourself a real chance of acceptance:**

1. **Search the repository first.** Most obvious detections already exist.
   Duplicates are the commonest rejection reason.
2. **Look for genuine gaps.** A technique with no rule, a new LOLBin from LOLBAS,
   or a variation an existing rule misses - the kind of gap you found by
   multi-atomic validation in the last step.
3. **Follow the contribution guide exactly** - naming conventions, file location,
   required fields, and the rule creation guide's style rules.
4. **Test the conversion** for at least two backends before submitting.
5. **Complete `falsepositives` honestly.** This is scrutinised.
6. **Expect review comments and engage with them.** Maintainers are helpful and
   the review itself is a free education. Revisions are normal, not rejection.

<Callout type="key">
Even an unmerged pull request with substantive review discussion is worth
including in your portfolio - it shows you engaged with a professional open source
project and took feedback. A merged rule is better, but the attempt is far from
worthless.
</Callout>
